# Chunks: permanent agent operating contract

**Mission:** Build Chunks into a colourful, deeply usable **Android-native BitTorrent client and first-class rTorrent remote**, with intuitive Places, independent Collections, clean optional display aliases and safe control of seeding data. No functionality is considered delivered merely because it is written into a specification.

## Product invariants

- Transfer identity = engine/server scope plus verified infohash; **Place** = actual accessible storage root and privileges; **Collection** = semantic many-to-many grouping. Original torrent name, Chunks-only display alias, file mapping, derived independent library copy and approved destination suggestion are separately represented.
- A user choosing a Place at Add selects the actual **parent destination** for local or remote engine. A string setter, preview or acknowledged RPC is not a verified physical move. Refuse unsupported operations or offer a safe deferred move or independent library copy; never invent one-click portability across SAF/providers or managed remote hosts.
- A display alias edits **only** Chunks metadata. A source-only name suggestion must remain an editable proposal; don't infer celebrity guest, episode title or show identity absent from source. No auto-rename, auto-delete, implicit organization move or transfer-side effect from a suggestion.
- `d.erase` is **session-only** and must not be conflated with deleting payload. Backing-file rename, relocate, copy and cleanup require independent capability, fresh exact-object target, shared-reference checks, journal/recovery and verified seeding postcondition. Keep original source for library copies and archive extraction.
- XML-RPC via authenticated TLS is the direct rTorrent baseline; optional Companion is **not** required for everyday remote control. rTorrent/rakshasa libTorrent is different from the phone's Arvid libtorrent4j. Capability-check individual builds, auth proxies, views, methods, integer encodings and filesystem providers rather than version guessing.
- Distinguish requested, attempted, acknowledged, verified, uncertain, refused and post-failure recovery. **Never blindly retry a remote mutation after a missing acknowledgement**. Refresh is observation, not proof no concurrent actor modified server state.
- Optional local storage caps are independent of remote storage; warnings do not enforce quota. No automatic removal of files needed for sharing, not even extracted source archives. Auto-extraction off by default; do not equate the merged bounded manual ZIP-to-SAF path with arbitrary archives or device acceptance.
- No guaranteed Android background uptime, unrestricted filesystem, real physical handset UX or cross-provider SAF success without device proof. Validate API-level FGS policies, process death, grants, net changes and battery limitations.
- Primary interactions must include 48dp-class targets, 200% text, TalkBack/keyboard and gesture alternatives, reduced-motion and status distinctions. Bright personality must not hide destructive results, warning text or error recovery.

## Owner-authorized test data and destructive scope

The owner designated one connected Seedhost rTorrent instance as **nonconfidential development inventory**, permitting ordinary nonsecret torrent names/paths/statuses in sanitized public fixtures, logs and native visual QA. The owner also permits **destructive torrent testing on that development instance**, limited to reviewed exact-hash single-target Adds, lifecycle/priorities, Remove and appropriately proven mutation paths with preflight, independent verification and recovery. It is **not** authorization to expose credentials, cookies, passkeys or tokens, mutate unrelated hosts/accounts, use arbitrary shell, or remove backing files without the separately gated ownership and crash-safety proof. See [SEEDHOST-REMOTE-TESTING](docs/SEEDHOST-REMOTE-TESTING.md). Public Add fixtures: licensed [Internet Archive/Wikimedia corpus](docs/PUBLIC-TORRENT-FIXTURES.md); never random tracker URLs.
