## Batched exact-source validation (mandatory)

**Installed debug APK routing:** The [shared PR workflow](../.github/workflows/native-add-instrumentation.yml) admits the checked ordered union of [per-family route patterns](../tools/ci_shared_debug_routes.json); the [selector](../tools/ci_shared_debug_routes.py) resolves the full PR changed-file set, including renames, with head/base/count revalidation. Unknown, stale or incomplete metadata conservatively selects all families. Native and Universal Add require one source/tree/checksum-bound, attempt-scoped app/test pair. Other selected disposable installed families consume that pair when available; if no Add build was required, they retain their independent build path. Never fall back after a selected producer fails. Standalone manual workflows retain their own isolated execution and the supported exact-source manual producer contract. Scope `both` preserves Native + Universal Add, `all` explicitly selects every registered family. R8, preview/live, foundation and protected-host workflows are not interchangeable artifacts. Keep route-manifest parity, full per-family verifiers and exact gate identity checks; an unexpanded skipped caller or matrix check cannot prove a child executed.

Map each test to authoritative requirement, test intent, changed boundary and independent positive/negative witness. Batch cheap docs/static/affected JVM and compile checks; run targeted API29/API35/R8 or authorized real-peer tests for impacted Add, JNI, auth, identity, privacy, navigation, storage and lifecycle. One reconciled assembled candidate receives full native verifier, Android foundation, R8 and real-peer assurance, re-running gates invalidated by later changes. Build once and reuse only identical verified APK bytes. No emulator for docs-only and no duplicated full cross-branch WIP fanout. Diagnose red cases as product defect, obsolete literal/screenshot expectation, fixture or infrastructure without removing enduring assertions; a rerun alone never confers acceptance. Measure time to actionable failure, queue/setup/compile/emulator and redundant runner minutes separately. [Completion order](COMPLETION-ROADMAP.md).

**Mandatory contract preflight before expensive work:** For any accepted change to UX, identity, schema, test evidence or a lifecycle contract, inspect affected requirements **before** Android/Gradle/real-server setup. Trace old and new names through asserting tests, semantic locators, screenshot producers, consumers, fixtures and workflow selectors. In the current PR record KEEP / REWRITE / REPLACE-EVIDENCE / RETIRE / BLOCK for consequential obligations; preserve security, privacy, exact-client, recovery, authorization and data-integrity oracles. Resolve demonstrably obsolete expectations and run existing cheap source/collector checks (such as `tools/check_compose_capture_contract.py --preflight` and `tools/check_native_atlas_contract.py`) before device tests; these static checks are evidence plumbing only. Small unchanged contracts need a proportional quick scan, not a blanket test-inventory project. A manual `workflow_dispatch` bypassing normal path selection still needs this same preflight.

**Batch implementation without hiding failures:** Use draft PRs for related small edits and inexpensive tests; review the complete changed-file dependency closure and shared fixture/compiled APK opportunity at integration. A ready main-targeting PR then receives required **exact-head** validation, using artifact SHA/byte identity for safe reuse and independent per-client/per-test receipts. Do not run a full native matrix on every speculative branch or treat a previous PR head, a cancelled job, skipped workflow or successful retry as current acceptance. Risky auth, Add, storage, operation and mixed changes still need their appropriate installed and real-engine negative gates.

## CI event routing and relevance

**Only PRs targeting main auto-dispatch validation.** Every `pull_request` workflow must declare `branches: [main]`. GitHub evaluates this filter against the PR's **base** branch, before allocating runners. A reverse synchronization PR (`main` into `ci/feature`) therefore must not run any automatic CI. The real feature PR targeting `main` still receives the exact-head relevant suites, and explicitly authorized `workflow_dispatch` remains available for other bases. Never interpret skipped/non-dispatched checks on a non-main PR as acceptance for a main merge. Do not use reverse integration PRs merely to update feature branches; prefer a bounded, reviewed ref update and test the final main-targeting candidate once. The offline routing test guards this destination-branch policy across all workflow files.

**Trigger audit:** GitHub pull_request path filters apply to the *whole PR diff*, not merely the newest commit. Thus a docs-only amendment to a ready PR containing earlier production changes still qualifies its production CI; the current exact-head requirement means the relevant gate needs an executed result on the accepted revision. Batch work on draft PRs, mark ready once integration is stable, and avoid changing ready PRs without a reason. Do not disable synchronize events, claim skipped checks passed, or silently reuse older-head proof.

**Cheap routing-only changes:** Editing the Android foundation or native Add workflow's path filters no longer automatically launches a full build or emulator suite. Documentation validation owns those definitions and runs offline routing/contract checks. Changes to executable build commands, dependencies, emulator configuration, sharding or acceptance assertions **still require explicit workflow_dispatch of the affected suite on the candidate ref** before merge. A routing-only PR must say why a device run is irrelevant; the absence of a workflow is not a pass.

**Dedicated test ownership:** Native Add excludes only exact instrumented test source files with a dedicated installed Android workflow (e.g. Compose 200% font scale, real combined-server, storage/source archive, launcher/font). An edit to the owning test must be accepted by its own installed workflow. Production changes, mixed changes and any new shared instrumented test still route to native Add. Negative exclusions must not match shared code or package folders.

**Workflow-only merge deduplication:** When a font/render or portable workflow file changes without its actual source assets or tools, validate event routing in Documentation CI at PR time rather than running expensive font jobs once in the PR and again after merging. Remove workflow-self paths from both PR and main-push filters for costly render workflows; retain their real source/asset triggers and workflow_dispatch for deliberate runtime proof. Portable Skills keeps its inexpensive PR self-check but omits workflow-self main push. Legacy protected read-only Seedhost diagnostics are manual-only, never retriggered by editing their own YAML. Main Pages deployment remains push-triggered because publishing changes is an actual delivery action.

**Push / merge controls:** Every automatic push workflow must specify both a bounded branch filter and relevant path filters. Ordinary feature-branch pushes should not run a second portable Skills job beside the PR check; push verification of merged Skills on main remains intentional. Historical named-branch workflows are exceptions only for their exact old branch. Protected remote mutations, release builds and APK publishing retain explicit manual authorization.

**Local audit:** The offline routing policy test inspects all GitHub Actions workflow files, verifies every PR/push filter and exercises synthetic examples for docs, Skills, dedicated tests, new shared tests, production code and mixed PRs. Run: python3 -m unittest discover -s tests -p test_ci_event_routing_policy.py. It runs in Documentation validation and proves dispatch eligibility, not actual GitHub scheduling, source-matched Android execution or visual acceptance.

GitHub may evaluate only the first 300 paths in some PR comparisons and treat huge changes differently; absence of an automatically selected check is never accepted as proof that a required gate is irrelevant.

**Visual specimen deferral:** The native visual atlas job allocates a runner only on manual dispatch during the owner-deferred phase. Preserve its established candidate routing and capture/test plan for reactivation. Record the deferred atlas as an explicit scope waiver when running an integration acceptance report. Functional Android and accessibility checks still apply.

## Select the smallest sufficient truthful checks

1. Determine actual changed source files, runtime surface and dependency graph. Run offline format/docs/JVM tests first, then targeted instrumented Android/real disposable server and applicable R8 checks. Do not launch every emulator for a documentation-only change or add new workflows when an existing shard can carry the case.
2. Changes to shared Add, source/identity, activity navigation, persistence, remote RPC or operation gating require their relevant installed actual user journeys and negative controls, not mock-only approval. Android UI changes require proportionate IME/TalkBack/semantic and layout checks on the primary Pixel target, with secondary narrow/large-font matrices selected by risk; media enrichment changes require real consent/network/provider plus no-request negative checks. UI-affecting PRs also need an explicit [experience-contract](FEATURE-EXPERIENCE-CONTRACT.md) note and review of representative actual-render evidence when the presentation changed. A passing screenshot-capture/atlas check does not verify its appearance.
3. Use approved CI selectors and build-once artifacts where byte identity can be independently verified. Do not reuse a previous head's APK/test result for changed source; require source SHA, Git tree and actual tested APK digest to match the accepted candidate.
4. Preserve full native Add shard coverage and final verifier; never reduce test counts or skip a failing test to force green. Respect the case-count/receipt rules in [CI-EVIDENCE-AND-RUNTIME-CONTRACT](CI-EVIDENCE-AND-RUNTIME-CONTRACT.md).
5. Genuine BitTorrent acceptance requires actual verified pieces/peer evidence in disposable authorized servers and installed phone clients. Server RPC ACKs, mock peers, started flags and cached size are insufficient. Protected host tests require the existing explicit authorization and secrets policy.

## Installed APK provenance must survive failed journeys

For each disposable installed Android journey, establish the exact checked-out source SHA and Git tree, actual debug/preview application ID and version, built APK candidate bytes, pulled **installed** APK bytes, size and SHA-256. A byte-for-byte compare may prove equality but its silent successful exit is insufficient to **report a hash or byte count**. Add bounded source-bound safe provenance output to the actual installed gate and durable receipt, including runs where later network/Details/lifecycle steps fail. Never substitute a historic APK digest, a test APK digest, an artifact ZIP hash, an Android JUnit digest, or a later rebuilt APK for the installed candidate. Keep raw host/device paths, private endpoints, auth headers, passkeys and pulled binary out of public logs; delete the temporary pulled APK after comparison. Record a missing digest as an evidence gap, not success.

## Shared native-focus failure diagnosis

If the installed native Add shard reports `ClipboardUriIntakeInstrumentedTest.singleCopiedUriPrefillsButAmbiguousOrUnrelatedUrisNeverDo` at the **foreground window focus** precondition, preserve the executed failure. Inspect the actual focused window/activity and owning package, UI/system overlays, emulator API/startup and JUnit receipt before making a QA-only fixture change. Keep the explicit foreground requirement and all clipboard-source negative assertions; never skip the case, remove focus preconditions, or classify earlier red runs as green. Avoid separate speculative test patches in each production branch. A validated QA correction must run full native shards/verifier at the exact integrated source.

## Diagnose red CI before modifying a test

- Identify exact tested SHA, workflow/run/attempt, stage, expected and executed case identity, last safe checkpoint and environmental preconditions. Distinguish checkout/build, emulator boot, fixture setup, assertions, network/auth/provider refusal and CI infrastructure faults.
- Preserve the first genuine red and all retries in the ledger, even after a passing fix. Do not rerun indiscriminately: isolate failing proof, fix the cause and rerun the full required gate on the exact changed head.
- If the runner never reached a new assertion, say so explicitly; do not classify that assertion passed or failed. No all-skipped or missing receipts accepted.
- Never print private credentials, tracker tokens, user paths or raw server errors in CI logs, artifacts, PR descriptions or public issue text.

## Test design and exact-commit acceptance

Write and change tests by [TEST-ARCHITECTURE](TEST-ARCHITECTURE.md): stable semantic ids for enduring capabilities, outcomes over presentation, screenshots as evidence unless an approved baseline exists, and explicit reconciliation (never deletion or weakening) when a UX change is deliberate. Classify every red or missing result as product failure, test-contract drift, environment/dependency or **not executed**.

**Draft PRs skip the native, R8 and installed-magnet jobs; skipped is not passed.** Mark a PR ready so every gate runs on the current head, then run `python3 tools/pr_acceptance_report.py --sha <exact head> --profile integration` (`integration-real-peer` when Add, source intake or remote Add changed). It exits non-zero unless every gate in [`tools/acceptance_gates.json`](../tools/acceptance_gates.json) executed and passed on that exact commit; waivers need `--waive GATE=REASON`. Evidence from another head, a parent PR or a different workflow mode does not qualify this commit. Adding or removing a native screenshot producer requires the matching entry in [`tools/native_atlas_manifest.json`](../tools/native_atlas_manifest.json).

## Merge and release acceptance

The integrator must independently review PR diffs, source ancestry/overlap and required check execution. Green on an older parent does not qualify a rebased dependent. Use current GitHub state, not a dated handoff, before merging.

A source-matched installable debug APK may be identified as a tested pre-alpha only after confirming exact source and independently hashing the **actual installed and tested** APK bytes. Record the receipt in the owning PR/issue; use the [evidence index](QUALITY-LEDGER.md) for archives. Physical Pixel, protected Seedhost, publisher-signing, OEM/Doze and human accessibility are separate evidence tiers and cannot be inferred from emulator tests.

## Time and cost discipline

**Disposable emulator snapshots (owner-authorized 2026-11-25):** Clean AVD snapshots may be deleted as soon as their intended tests have finished. The measured API35 software-renderer pilot failed both restores; persistent AVD caching is retired, and the manual cold baseline does not write an AVD cache. Prefer ephemeral same-runner storage for any future boot-reuse experiment; any cross-run experiment must include generation, SDK provisioning, transfer, restore and cleanup costs. Do not cache a populated device, ADB keys, app data or credentials; do not grant PR jobs cache-deletion or other write permissions. A future trusted cleanup may delete only verified pilot-owned snapshot keys after their consumers settle, never unrelated Gradle caches. Do not sacrifice useful Gradle cache capacity or increase paid storage merely to retain an AVD. See [the snapshot pilot](CI-AVD-SNAPSHOT-PILOT-2026-11-03.md).

**Cheap workflow authoring preflight:** Parse every workflow and local composite action YAML with a real syntax parser; text-level routing tests alone cannot detect malformed scalar or indentation. Independent offline validation groups should execute after another group's failure, without continue-on-error or a green overall job. Syntax success does not establish valid Actions expressions, execution or accepted device evidence.

Reuse genuine fixtures, cached Gradle and signed-off source artifacts only where compatible. Prefer narrow ordered feedback to parallel full-suite fan-out; measure actual runner minutes, attempts, source heads and failure cause before proposing costly changes. Keep always-emitted merge status and safety gates intact. Do not turn optional workflow skips into a passing acceptance claim.

For **Chunks R8 minified smoke**, keep the exact-source qaMinified app and instrumentation APK build, executed installed API35 case, strict source/run/JUnit receipt and mapping output. Keep the Gradle daemon warm between build and connected test as implemented in merged #1510; inspect the emitted build and installed-test seconds. Target normal job execution under 10 minutes, investigate sustained executions over 15 minutes, and treat sustained executions over 20 minutes as CI performance regressions. Differentiate GitHub runner queueing from execution and compare like-for-like exact-head runs; do not change acceptance assertions or skip emulator proofs to meet a duration target.
