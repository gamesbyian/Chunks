# Intake, queue, scheduling and discovery policies

> **Authority:** feature-level product/UX/technical contract for previously under-specified ecosystem inventory items. The binding owner outcomes remain [PRODUCT](PRODUCT.md), [UNIFIED-ENVIRONMENTS](UNIFIED-ENVIRONMENTS.md), [CREATE-AND-SHARE](CREATE-AND-SHARE.md), and [SMART-SEEDING-RULES](SMART-SEEDING-RULES.md). Item IDs **Fxx.yy** refer to the independently researched 240-item catalogue in [research PR #537](https://github.com/gamesbyian/Chunks/pull/537). This contract does not adopt all 240 features. **Status: specification target; no new implementation or verification implied.**

## Scope and boundaries

This contract closes ambiguity for **21** catalogue items: F01.03/05/18; F02.05/06/07/08/11; F05.02/05/07/08/09/10/11; F06.08/14; F07.08/10; F12.11; F15.09. It covers Android-local and one or more individually named rTorrent environments wherever demonstrated; it does not add non-rTorrent remote engines or require an always-on cloud controller. Tracker credentials and service account access are optional. Existing owner-approved Smart Seeding Rules are owned exclusively by [SMART-SEEDING-RULES](SMART-SEEDING-RULES.md): this contract adds orthogonal *download/queue/network* policies, not a conflicting ratio-rule system.

**Terminology:** an **intake source** is a single file, URL, magnet, share intent or authorized feed/watch source; an **environment** is the on-phone engine or exact remote server profile, with immutable ID; a **policy** contains conditions and actions; **effective state** is an engine-observed value, not a saved preference. A user-level rule/group, an engine-native throttle/queue group and a remote server script are separate identities. Session-wide counters and time-series observations retain source and sampling provenance.

## Intake sources and credential boundary

- **F01.03 URL metainfo acquisition:** Accept an explicitly supplied HTTP(S) URL that resolves to a bounded, validated torrent metainfo file, or a magnet URI; distinguish fetching the *metainfo* from fetching the *payload*. Show origin host, destination environment, final filename/metadata and actionable error before Add. Disallow automatic private-address/loopback fetches, cross-origin credential forwarding, redirect credential leakage, unsafe schemes and oversized content; never treat an arbitrary webpage as a torrent. A server-side Add-by-URL is separately capability-verified and cannot bypass Chunks' metadata validation. Prefer device-side fetch followed by exact target Add where legal/possible. Require explicit approval before crossing privacy boundaries with a torrent URL.
- **F01.05 alternative intake channels:** Treat RSS/Atom and supported indexer feeds as **Discovery-managed** optional connectors; treat user-configured local watched-folder auto-loading and explicit URL/QR imports as **ordinary intake** independent of the Discovery master switch. Both paths use the same validated Add draft, dedupe, destination and seeding-group rules, but retain separate enable/auto-start authorizations. Remote watch-folder writing requires a separately authorized file adapter, never inferred from RPC. Android background restrictions may defer polling; never advertise 24/7 scanning. Third-party indexer APIs, shell/CLI and externally orchestrated intake are integration adapters, not universal built-ins, and must be individually approved/capability-gated. Source lists and unattended auto-start have separate opt-ins, source-level enable/disable and preview. QR decoding must be on-device and never silently follow/open a decoded URI.
- **F01.18 authenticated metadata retrieval:** Store *retrieval-source* accounts separately from remote engine logins and Create & Share publisher profiles. Support only source-specific documented mechanisms (e.g. token/session/cookie) with least scope and explicit expiration/revocation; never guess login cookies, scrape login challenges, or forward credentials to a different origin. A private .torrent or passkey-bearing URL is sensitive in exports, notifications and clipboard. Auth failure preserves an editable draft rather than falling back to anonymous/public sources without consent.

## Integrated torrent discovery and its master off switch (owner binding)

**Decision D-DISCOVERY-20261029.** Chunks SHALL offer an integrated **Discover** experience combining supported public/private indexer search, user-selected search providers, RSS/Atom subscriptions, saved searches, matching/quality rules and optional automatic intake. The user must be able to disable **all Chunks-managed torrent discovery** with one persistent, accessible **Enable Discovery** switch in **Settings → Discovery** (and a shortcut in the Discover screen). Discovery does not require a Chunks account, developer-operated search relay or particular provider; opt-in source accounts may be used where the service allows. Provide a useful multi-source search without making users install another app, but be candid about unavailable sources, credentials, rate limits and search coverage.

### Product boundary and defaults

- **Disabled until enabled by the user.** No background feed polling, remote index querying, third-party metadata lookup or network-initiated search merely because Chunks is installed, a remote profile is connected or an Add draft is opened. The Discover entry may show a local explainer/Enable action while disabled; once enabled, users may turn it off again at any time, without losing configured sources by default.
- The master switch gates **search, suggestions, saved-search refresh, indexer synchronization, RSS/Atom/IRC announce discovery, provider-driven watched sources, catalog/category lookups and discovery-triggered auto-add/auto-start**. An off state is enforced on every discovery adapter and dispatch, including process restart and disconnected/reconnected profiles. All discovery source-level enable toggles and per-source credentials remain saved but inactive; users may separately clear discovery history, remove providers and revoke stored credentials. Turning off does **not** disable Android Open with, manual magnet/.torrent/URL/QR imports, separately authorized direct auto-loading from local watched folders or inbound file/share intents, ordinary Transfers/Places/Collections, existing Smart Seeding Rules for those Adds, or the separate **Create & Share** publishing workflow.
- On Disable, immediately cancel or prevent new discovery network requests, polling, future triggers and unsubmitted auto-add actions. Preserve already submitted torrent jobs and payload, and do not stop active downloading/seeding, reverse an already-accepted Add or delete source configuration. For in-flight submission with unknown result, stop further dispatch and reconcile exact target/readback on next permitted manual action; report what was already committed. Pending discovery proposals remain inert until re-enabled and reviewed. No tracker-contact requests through discovery while disabled; normal tracker communication required by **existing active torrents** remains unaffected.
- Separate **Enable Discovery**, **Allow automatic intake**, and **Start automatically after auto-add**: enabling search never enables automatic downloading/seeding. Feed/watch/IRC background monitoring and push/notification actions require their own affirmative consent, with Android power/lifecycle limitations disclosed. Discover-off must prevail over all saved sub-settings. Existing smart seeding group assignment still applies to torrents explicitly added through other routes.

### Find, inspect and select

- **Discover** provides a clear search field, multi-source provider picker, search filters, sort and results. Source registry supports public and user-configured private indexers through reviewed documented APIs or compliant local provider adapters (including Torznab-style normalized outputs where compatible). Plugin/template discovery/update/disable is bounded, versioned, signed/verified where feasible and never arbitrary executable code from a search page. An unsupported, expired-auth or blocked provider is shown with a specific explanation; no stealth alternate scraper, CAPTCHA bypass, account pooling or hidden relay.
- Normalize result identity with infohash/v1/v2 information when supplied, source-specific ID, title, published date, size, content category, seed/peer estimates and tracker/provider provenance. Display unknown values as unknown; do not fabricate accuracy or safety ratings. Group likely duplicates by **verified matching identifiers** while retaining original provider/quality differences; similar titles alone never warrant auto-merging or overwriting an existing torrent.
- Provide filter and saved-search controls for keywords, tracker/source, category, file size, publish age, seed counts, language, quality, season/episode, codec and exclusion rules. Results and filtering decisions show source, matched rule and rejected/uncertain reasons; expert regex is bounded and tested against resource exhaustion. User can compare candidates, inspect metainfo/permissions where obtainable, and choose **Add** to the common Add review with exact phone/server target, Place, start toggle, seeding rule and download policy. Never auto-start merely by tapping a result.
- **Subscriptions:** Users can configure RSS/Atom (and compatible site APIs), preview entries, mark read, manage history, specify refresh cadence, conditionally match, notify or draft/Add. Do not imply every indexer has RSS, universal freeleech detection or permission to fetch private metadata. Feed refresh is throttled/backed off per provider; offline Android does not guarantee continuous polling, so missed releases/history availability must be explained. On reenabling Discovery, do not silently replay all old results or auto-add a backlog. Require preview, dedupe and a configurable lookback/first-run baseline.
- A source or result that is private, risky, ambiguous, mismatched or blocked retains an actionable status without exposing passkeys in UI, shared export or logs. Per-provider session, proxy, query data disclosure and retention follow [SECURITY](SECURITY.md). A user-initiated manual Add via another path never inherits a hidden search/source setting.

### Navigation and configuration

The normal primary navigation remains **Transfers / Places / Collections / Servers** and the Add workflow. When enabled, Discover is directly reachable from a clearly labelled search action in Add and a discoverability shortcut in an overflow/secondary navigation surface; it may be a distinct destination, but must never replace the main Transfers screen or conceal Start/Stop/Add/File actions. When off, hide or collapse active discovery suggestions/shortcuts while leaving the Settings switch and an optional clear **Enable Discovery** entry discoverable. A user can disable discovery from its screen in one action without digging through provider settings. Discovery state is Chunks-wide; provider lists, saved searches and automatic-intake rules have separately scoped target environments.

### Acceptance for discovery

1. Fresh installation, local-only, remote-only and combined profiles make **zero** unsolicited index/feed requests before enabling Discovery; an explicit manual .torrent/magnet Add still works.
2. Enabling Discovery exposes a tested multi-source search with filters, source and freshness, provider auth failures, dedupe, saved queries, RSS subscription and a reviewed Add draft; **search alone produces no new transfer**.
3. Disable while idle, fetching, offline, polling, with a pending proposal, during a race with auto-add, and after process death: no new discovery-driven lookup, notification or Add occurs; already accepted jobs remain intact; uncertain submissions reconcile.
4. Reenable retains sources without silently replaying historical entries or starting unlimited seeding; separate Discovery automation switches remain off unless explicitly chosen. Independently enabled local watched-folder/file auto-intake continues through a Discovery-off transition without the Discovery controller.
5. Authorized private-indexer credentials are isolated and redacted; request limits, unsupported services, lost permissions, malicious feeds and Android background restrictions are handled explicitly.
6. Discover toggle and Add entry pass 320×700, 412×892, 200% font, TalkBack and keyboard tests without demoting core torrent controls.

## Connected indexer services and optional cross-seed search

Existing-service adapters (such as an independently authorized Prowlarr-compatible source) are specified **only** in [EXISTING-SERVICE-INTEGRATIONS](EXISTING-SERVICE-INTEGRATIONS.md). They may contribute provider-labelled results to the standard Discover source picker and may be manually refreshed when Discovery is on; they are never general-purpose server administrators, NZB download engines or a reason to weaken the master off switch. Disabling Discovery also disables background indexer-source synchronization and discovery-driven cross-seed searches; a user can still import and locally compare an explicitly provided .torrent file without network discovery. Exact source/credential scope and tests are in that canonical contract and [CROSS-SEED-AND-PAYLOAD-COPY](CROSS-SEED-AND-PAYLOAD-COPY.md). These integrations are specialist secondary controls, not first-run mandatory setup.

## Queue, retries, history and liveness

- **F02.05 queue ordering:** Present readable user priority (Sooner / Normal / Later), optional explicit up/down/top/bottom reorder and queue position when the selected engine actually exposes mutable ordering. Moving a transfer within a filtered view must not reorder a hidden different transfer inadvertently. A Chunks-only visual order is never labelled as an enforced engine queue order. Distinguish queue priority from per-file priority and [Finish in Order](PRODUCT.md#multi-file-completion-order-finish-in-order-owner-direction-2026-10-27).
- **F02.06 concurrent slots:** Configure maximum active, downloading, seeding and checking jobs *per exact environment* only where native engine settings or an explicitly disclosed connected Chunks controller can enforce them. Validate ranges, conflicting quotas and inherited defaults; preview what existing jobs may pause **and which waiting jobs could start immediately**. Do not expose an unexplained numeric **0** when the actual engine would interpret it as *unlimited*, *disabled*, *no checking allowed* or *inherit*. Use meaning-first labels such as **Automatic / Limit to N / No concurrent checks** only when the underlying adapter can prove each consequence; otherwise explain the backend's exact zero semantics at entry and in the blocked-transfer state. Keep queued metadata acquisition distinct from actual data downloading, expose effective current rule, and require refreshed readback if a change is claimed applied. Settings must not imply persistent remote control when Chunks is offline. [Contextual state UX](UX.md#findability-and-truthful-outcomes-in-everyday-torrent-journeys-binding-ux-research-informed-2026-10-30).
- **F02.07 stall handling:** Distinguish queued-by-policy, no eligible peers, tracker outage, stopped, verifying, network-offline and genuinely no observed useful progress over a *user-visible configurable measurement window*. A stall detector may recommend freeing an active slot, but automatic rotation requires opt-in, a minimum observation interval, cooldown and fairness; never change tracker/seeding obligations or remove data on its own.
- **F02.08 retries:** Expose **Retry / Recheck status** for recoverable read and download conditions with bounded exponential backoff and cancellation. Never blindly retry ambiguous remote Adds, Starts, file writes, moves or deletions; reconcile exact hash and observed engine state first. Preserve cause, retry count, next attempt, target profile and last verified state across UI/process transitions. Auto-retry stops when permissions/credentials are revoked.
- **F02.11 history:** Retain an optional per-transfer activity timeline for add, actual state transition, tracker problems, downloads, queue decisions, user actions, rules and errors, labelled **observed / requested / inferred**. Prefer locally stored bounded/redactable records with retention and Clear history. Do not fabricate historic torrent speeds or a timestamp the server never supplied. Sensitive names/hash/paths/tracker hosts are absent from externally shared diagnostics unless separately reviewed; history deletion does not delete transfer jobs.
- **F12.11 watchdog:** A disabled-by-default Chunks-controlled watchdog can suggest or execute only individually authorized *non-destructive* rechecks/requeues after verified failure. Show which controller must remain running, stop on connectivity loss or uncertain command and avoid restart storms through capped attempts and cooldown. Existing native server schedulers may be observed but never overwritten merely because Chunks has a rule.
 
## Bandwidth, device and traffic policy

- **F05.02 alternate-speed calendar:** Support an optional named low-traffic profile and schedule per environment with explicit local-time timezone, weekday windows, daylight-saving gaps/overlaps and manual temporary overrides that expire predictably. Show which authority enforces it: server-native, phone engine, or Chunks-while-running. If none can enforce while Chunks is disconnected, offer **schedule only while app is active** or refuse unattended mode.
- **F05.05 quota limits:** Distinguish local transfer totals, rolling/monthly user-defined traffic budgets, actual measured metered-network traffic, and externally reported seedbox host/plan quotas. An unknown provider quota is **unavailable**, not zero. Define accounting reset time, timezone, upload/download inclusion, counter rollover/unknown values and early warnings. Do not promise an exact hard bandwidth cutoff from delayed counters; automatic hold/stop needs explicit opt-in, current measurements and acknowledged enforcement. Storage quotas belong to [STORAGE-AND-EXTRACTION](STORAGE-AND-EXTRACTION.md).
- **F05.07 conditional scheduling and F15.09 ISP/battery/Wi-Fi scheduler:** Offer simple **Wi-Fi only**, **unmetered only**, **charging only**, **battery above threshold**, and time-based policies on the phone; optional per-network profile only with Android-authorized network state. Explain temporary loss of access, OS power restrictions and battery precision. Remote transfers cannot inherit the phone's battery/Wi-Fi state by accident: they continue unless the user explicitly chooses **phone-dependent remote automation**, accepts that it works only when Chunks is online, and sees its controller status.
- **F05.08 network interface and ports:** For local seeding, expose verified interface/VPN binding and listen-port configuration only where libtorrent+Android can enforce it; monitor interface disappearance and fail closed for **VPN required**. Remote binding/ports belong to that server and must not be derived from the phone's VPN. Display provider/OS-managed ports read-only where not mutable.
- **F05.09 adaptive tuning:** Keep existing engine algorithms as default. Optional transparent optimization presets may adjust connection/slot/cache limits only within safe bounds, with a visible before/after, revert path, reasons and no silently downloaded benchmark traffic. No tuning during a measured instability or when required capability readback is missing.
- **F05.10 bandwidth isolation:** Isolate preferences and command targets by environment/profile; one profile's upload cap, privacy rule, scheduler or temporary boost cannot mutate another. If the OS or hardware shares an underlying network budget, label cross-profile contention as an estimate, not hard isolation. Native rTorrent groups are not interchangeable with Chunks group names.
- **F05.11 adaptive liveness:** For automatic stall recovery, combine reliable counter deltas, network/peer status and explicit minimum windows; throttle, slot-release, requeue and retry are individually consented actions with cooldown, per-environment capability/readback and audit. Never claim a job is dead from one zero-speed snapshot or start-flag.
 
## Search, classification and organization adjuncts

- **F06.08 search-source proxy/credentials:** Discovery-enabled index/feed/search connectors carry individually scoped authentication, proxy and privacy settings, not re-used rTorrent passwords or publication credentials. Make external query text, source names, outgoing endpoint and privacy/retention visible before the first enabled lookup. No blanket automatic scrape of private trackers or bypass of site restrictions.
- **F06.14 release/quality filters:** For voluntarily configured feed/search intake, allow bounded explainable filters for name, category, file size, language, season/episode, quality, resolution, codec and date. Preview matched and rejected samples, precedence and false-positive risk; do not silently rename, upgrade, replace or delete existing data. Uncertain media identity requests review. Do not require users to organize mixed collections into genre-specific root folders.
- **F07.08 notes/metadata:** Permit Chunks-local user notes and typed annotations separate from immutable torrent metadata, source title, file path, tracker tags and backend custom fields. They must be editable/exportable with explicit per-environment privacy settings, never transmitted to trackers or treated as authorization for file mutation.
- **F07.10 favorites and recents:** Offer Pin/favorite and bounded Recents for jobs, Places and views without modifying underlying engine priority. Persist exact environment+hash and identity-safe recency; deleted/locked/inaccessible items are hidden or marked unavailable, and clearing Recents must not delete files/jobs. Transfer history is distinct from Recents; no automatic sync to cloud.
 
## Shared UX and settings model

The shared Add review presents **Source**, **Environment**, **Place**, **Seeding group**, **Start after Add**, and, if active, the applicable **Download/queue policy**. Optional feed/watch rules appear in a compact source-detail sheet, not a compulsory wizard. Rule authors see **When → Then → Applies to → Preview**, with generated editable names where using Smart Seeding Rules; every row/summary identifies exact named environments. New profiles do not join existing automation by default. A transfer detail shows effective limits, enforceability, pause reason, schedule and history, with **Why?**, **Override for this transfer**, **Reset to inherited**, and **View errors**. Bulk edits show per-profile capability and before/after, avoid acting on stale selections, and separate preview from Apply. Touch targets, contrast, 200% text, TalkBack/keyboard, 412×892 and 320×700 remain mandatory.

## Failure, privacy and persistence

An intake/policy action has stable operation/source ID, target environment, source authorization, evaluated rule version, capabilities, request receipt, observed outcome and uncertainty state. Replayed Android intents are idempotent by explicit intent/source receipt plus exact metainfo hash once available. Duplicates across different engines remain independent; don't dedupe solely by torrent title. Secrets are encrypted and never in rule names, copied magnets, sample fixtures or diagnostics. Off-device resources are opt-in. Notifications explain held drafts, disconnected controllers, missing permissions and conflict with existing server schedulers. Do not auto-start unlimited seeding if a required speed/seeding cap cannot be applied. Never silently delete bytes or convert *retry* into destructive cleanup.
