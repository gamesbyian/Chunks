## Release focus and selection rule

**Immediate objective:** an independently reproducible, dependable BitTorrent client and Companion-free rTorrent remote, then a single cross-environment UI, then verified storage operations. Stabilize and maintain already-merged extras; **temporarily defer discretionary feature expansion** while P0 dependencies and acceptance remain open. This is a scheduling decision, not rejection of approved specs, a prohibition on critical fixes, or a claim that new physical-device evidence exists.

**Choose work in this order:** (1) red main / integrity / security regressions; (2) unclaimed, unblocked foundation or acceptance task in the **next executable** table; (3) parallel P0 integration or test infrastructure that cannot conflict with a claimed owner; (4) highest dependency-ready P1 storage task; (5) P2/P3 work only after prerequisite gates or explicitly approved separate capacity. If a device, secret, provider or owner approval is unavailable, record the blocker and take another unblocked **foundational** task. Never fill a hardware wait by default with an optional feature.

No new primary navigation, hosted infrastructure, unsafe file mutation or implicit remote elevation is authorized by this queue. Exact profile + infohash targeting, privacy, tracker-passkey safety, verified command postconditions, and source-data retention are non-negotiable throughout.
