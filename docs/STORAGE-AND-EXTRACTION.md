# Storage budgets, reclaim and archive extraction

Status: **owner-requested product scope, implementation pending** (2026-10-24). Canonical product boundaries: [PRODUCT](PRODUCT.md), UX authority: [UX](UX.md), implementation authority: [ARCHITECTURE](ARCHITECTURE.md), security authority: [SECURITY](SECURITY.md), execution priority: [WORK-QUEUE](WORK-QUEUE.md), tracking: [issue #70](https://github.com/gamesbyian/Chunks/issues/70). This specification does not claim local torrent-engine support, verified remote filesystem permissions, or accepted native UX.

## User outcomes and defaults

1. Set an optional **on-device Chunks storage cap** per volume/Place, inspect used/remaining/free, receive understandable tiered warnings and avoid filling the device. There is no automatic deletion of source data to enforce the cap.
2. See what can actually be reclaimed, distinguish removable Chunks-managed independent files from active seeding dependencies, and use a compact **cleanup wizard**. Batch review is possible but never conceals destructive consequences.
3. Extract a completed archive immediately or opt into extraction when its constituent download files are verified complete. Source archives remain intact by default even if successfully extracted. Extracted files are independently managed and never silently substituted for seeding data.
4. See explicit, factual consequences **in the review screen before approving** any choice that removes bytes relied upon by one or more torrents. A missing archive will usually make affected torrent pieces unavailable and prevent valid complete seeding, even when extracted media exists elsewhere.
5. Keep local/remote semantics honest. Android device storage is not server storage. rTorrent RPC can remove a session, but remote payload deletion/extraction needs separately authorized verified filesystem operations.

## Storage accounting and quotas

- A budget is scoped by physical volume, SAF tree/root or engine-accessible Place identity, **never by visible directory label alone**. Show user-selected cap, actual file allocation where measurable, logical expected payload length, known remaining torrent bytes, Android-reported free bytes, reservations and anticipated peak extraction space; mark unknown estimates as unknown rather than conflating logical size with blocks allocated. Measure caches, partial files, staging, extracted output, independent library copies separately.
- Count physical objects once even if multiple transfers, Collections, paths or published views point to them; account for hardlinks, shared references, sparse files and deduplication uncertainty. If actual released blocks cannot be established, show **potentially reclaimable** rather than promised freed bytes.
- Proposed starter defaults, adjustable: warn at **70%, 85% and 95%** of the selected cap, with hysteresis, deduplication and persistent status in app; also surface device low-space signals regardless of cap. No push notification spam or repeated alert every polling interval. No default user-defined cap is imposed without consent; OS safety guard still applies.
- Show at Add and before extraction a forecast of target-volume headroom and estimated peak usage; the app should offer choosing another Place, stopping selected downloads, or adjusting cap when needed.
- **Local engine**: reserve usable headroom and safely pause affected new/in-progress *downloads* when projected writes threaten the cap or OS low-space floor; preserve existing completed seeding/upload paths, and require explicit resume/override. A hard numerical guarantee demands independent on-device enforcement testing under concurrent writes, sparse allocation, background lifecycle and app death. Do not claim one now.
- **Remote engine**: display reported capacity only if server/provider supplies reliable scope and timestamps. Cap defaults to **advisory**; enforce via server-backed limits only if proven. Phone cap must not pause a remote seedbox download. Where capacity cannot be obtained show 'Storage capacity unavailable'.
- Quota changes must not silently erase data already over cap. Explain that new writes are restricted while users choose a remedy. For impossible or stale measurement, warn without fabricating a precise cap status.

## Cleanup wizard

Entry points: storage dashboard, low-space warning, transfer file details and Places. Steps:
1. **Scope:** local volume or explicitly selected remote Place. Show fresh inventory time, stale/unavailable state and breakdown of backing files, independent library copies, extracted outputs, temporary/staged files, and unknown ownership.
2. **Find space:** default filter **Safe for sharing**; alternative **Include items that affect sharing**. Candidates sorted by verified recoverable bytes, age, access, ratio/seed health and source relationships. Distinguish 0-byte recovery for shared/hardlinked files and non-owned files.
3. **Review exact targets:** identify Transfer/engine and infohash/file index, visible title and actual storage path. For every selected action show what remains, what stops sharing, other references, how much space might be released, and whether recovery is possible. Separate 'Remove from Chunks/rTorrent session (keep data)', 'Delete backing data', 'Delete extracted result', 'Delete independent published copy', and 'Discard temporary files'. Unowned files cannot be included merely by directory proximity.
4. **Confirm:** a meaningful warning and separate explicit approval for any seeding-affecting deletion. Sample: **'This archive is part of a torrent. Deleting it will make affected pieces unavailable for sharing. Your extracted files will remain. To seed the full torrent again, restore or re-download its original bytes.'** Do not replace with generic 'Are you sure?'. Summarize multi-torrent impact on batch review. Offer cancel and preserve originals.
5. **Execute and reconcile:** capability/ownership/reference recheck; durable journal/staging as supported; accurate pending, deleting, verified, partial, uncertain, and recoverable/irreversible statuses. No blind retry after an ambiguous response. Report verified released space, not merely predicted savings. Do not promise undo without an actual Trash or recovery implementation.

No automatic recommendation executes a destructive mutation. Never follow symlinks, delete outside approved scoped roots, assume exclusive ownership, or delete while torrent mapping/write operations are uncertain. A shared physical file may block deletion even if one Transfer appears stopped. Native Android SAF deletion and remote assisted FS mutation have different permission/recovery gates.

## Archive extraction experience

- Per-completed-archive action **Extract now** and simple **Auto-extract when ready** switch in transfer details. Future-rule settings may apply to an explicitly approved Place/category, disabled by default, independent of organization classifier confidence. The per-transfer toggle may optionally apply to *this transfer only*. An obvious settings screen can inspect/revoke approved auto rules.
- Destination: choose original containing directory when permitted, separate local folder or independent library Place. No remote archive extraction via rTorrent RPC alone; if source is remote, require safe authorized remote filesystem provider or an explicit download-to-device workflow with its own storage forecast.
- Extract on verification of all source bytes required by that archive set. For incomplete multipart groups, pending pieces, bad CRC or unstable I/O, explain waiting/failure. Multiple archives in one torrent may each become eligible independently. Do not assume a torrent's single 'completed' flag alone validates archive group integrity.
- Support formats incrementally after evaluating library security, maintenance, licenses and Android integration. ZIP is initial target; 7z, RAR, multipart and encrypted archive compatibility are separate tested capabilities. If a password is needed request it interactively, never silently store it. Avoid retry storms for permanently unsupported formats.
- Preview archive contents, file count and known expanded size, destination and worst-case temporary staging demand; when unknown show uncertainty and apply bounded streaming limits. Users can choose collision policy **skip, rename, or explicit overwrite** with preview; no silent replace. Keep originals by default. Extracted files become provenance-linked independent artifacts with own deletion rules.
- Use bounded streaming extraction, check **actual** accumulated decompressed bytes, ratio, count, depth, member names, traversal, absolute paths, Unicode/case collisions, symlinks/hardlinks, special files and zip bombs. Normalize and constrain via handles/SAF scope; declared header lengths alone do not establish safety. Limit concurrent jobs; cancel/cleanup partial output safely; survive process death with idempotent operation IDs and reconciliation to avoid duplicate output.
- On-screen status: waiting for verified bytes; estimating; requires password; unsupported format; extracting (progress); verifying; complete/open result; failed/retry; partial/recovery. Accessibility: 48dp targets, TalkBack-specific description of consequences, 200% text, no status conveyed by colour alone.

## Implementation and independent acceptance

**S1: Domain/accounting and dry-run** (can be built before local engine). Pure models for immutable FileObject/StorageRoot/References, byte estimates with confidence, quota policy, safe/requires-confirmation/blocked impact classification. Unit fixtures: same backing bytes in two torrents; hardlinks; sparse/partial files; multi-file torrent; library copies; extraction larger than archive; stale inventory, negative/overflow sizes, space exhaustion, multi-volume and network unknown.

**S2: Extraction local slice**. Prove safe ZIP extraction against a real completed local archive, strong bounds and malicious corpus (traversal, bombs, duplicates, partial/multipart, password, interrupted extraction). Validate on Android volume/SAF access and exact produced bytes. No auto-extract until manual service and crash recovery pass.

**S3: Quota enforcement** (depends on real local engine and Android file I/O). Tests for threshold crossings, real low-storage, concurrent writes, pause/resume while uploads continue, kill/restart, distinct volumes; optional remote advisory metrics from verified capabilities.

**S4: UX dashboard / cleanup preview**. Native Compose screenshots on compact and large text viewports, TalkBack, uncoached comprehension of 'delete archive breaks seed' and separate session vs payload actions. Real delete operations only after S5 capability and recovery tests.

**S5: Verified cleanup executor and remote extensions**. Disposable filesystem volume, cross-references, concurrent writers, symlink and path attacks, fault injection at every journal state, server disconnect/ambiguous ACK, user-confirmed deletion, actual byte remeasurement and torrent status validation. No ordinary remote delete/extract button before independent filesystem authority proof.

For every slice record exact SHA, tests, source fixture, Android/engine/remote topology, observed results and open evidence gaps in QUALITY-LEDGER. A merged document or mock screenshot is not working storage management. Preserve R1/R2 compatibility/Add as existing critical path unless product owner reprioritizes.
