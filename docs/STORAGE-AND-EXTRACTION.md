# Storage budgets, reclaim and archive extraction

## Optional external final destinations (planned)

When an **On phone** torrent is intended for Google Drive/SAF or an authorized FTP-family Place, the initial implementation stages its payload safely on phone and then publishes an independently verified copy. Download completion, stable source readback and final destination verification are separate milestones; keep local payload and existing seeding by default. No auto-delete on upload acknowledgment, no silent foreign-path overwrite, no assumption that SAF is a native random-write torrent filesystem. Full authority and failure acceptance: [EXTERNAL-DESTINATION-DELIVERY](EXTERNAL-DESTINATION-DELIVERY.md). This does not supersede existing P0 native collision safety or claim physical provider acceptance.



Status (2026-10-26): **partially implemented.** Optional saved **phone app-download-folder logical advisory** GiB target, 70/85/95/over-cap warnings and persistent hysteresis (#174), dry-run cleanup models, OS-space observation, a separate bounded read-only **POSIX allocated-block/inode survey** (#176), bounded ZIP inspection and **manual extraction into a newly created SAF folder with journal/recovery** (#119/#120) are merged. The allocated-block UI (#182) and same-volume fence (#185) passed scoped API35/JVM acceptance but do not establish reclaimable bytes, physical provider safety, verified ownership or quota enforcement; native loopback integrity anomaly at #182's first CI attempt remains tracked in issue #5. A completed local transfer can be copied independently into a user-selected SAF library folder (#147), with source retained. **No verified enforced per-volume cap, physical cleanup deletion, auto-extract, arbitrary remote file mutation or physical provider/device acceptance.** Independently publishing a finished local torrent to SAF now requires confirmed libtorrent `CACHE_FLUSHED` (#193) before any destination is created, because native completed/seeding state alone may precede stable filesystem readback; this is not proof that concurrent external mutation or power-loss cannot alter source bytes. Canonical product boundaries: [PRODUCT](PRODUCT.md), UX authority: [UX](UX.md), implementation authority: [ARCHITECTURE](ARCHITECTURE.md), security authority: [SECURITY](SECURITY.md), execution priority: [WORK-QUEUE](WORK-QUEUE.md), tracking: [issue #70](https://github.com/gamesbyian/Chunks/issues/70). ## Native backing-file collision safety (P0, 2026-10-29)

An independent two-peer native desktop test [#633](https://github.com/gamesbyian/Chunks/pull/633) proved that a torrent started into a folder containing an unrelated same-relative-path file **overwrites that file**. Merely adding the torrent stopped did not change it. This is a real destructive boundary, not a theoretical risk.

**Contract for every phone Add source** (torrent document, magnet, snapshot, shared intent and future automation):

- Survey the exact native save root and each metadata-known non-pad relative payload path before permitting payload writes. A target file with uncertain or foreign ownership, a path through an unexpected link, or an inaccessible parent must result in refusal or a safely blocked, non-writing transfer. Name/size matching does not authorize reuse.
- A magnet may fetch metadata in upload-only/no-payload mode. After discovery, validate its newly known paths **before clearing upload-only or honoring previously recorded Start consent**. Revalidate a stopped metadata-ready magnet on explicit Start, and demonstrate a blocked transfer cannot become writable after restart.
- Allow legitimate verified reuse/seeding through a separate explicitly reviewed attach-existing-data path, with provenance and native hash/piece recheck. Do not categorically prohibit every nonempty download folder.
- The merged read-only checked Add in [#640](https://github.com/gamesbyian/Chunks/pull/640) is a point-in-time preflight and cannot lock Android public Downloads against an external rename, mount or symlink race, including a foreign file introduced after Add. Dependent magnet work [draft #648](https://github.com/gamesbyian/Chunks/pull/648) remains blocked by an observed VERIFIED result where its collision Start test required UNCERTAIN; restart retention was not reached. Neither full magnet protection nor physical-device acceptance is established. [QUALITY-LEDGER](QUALITY-LEDGER.md) records exact heads and failed-run evidence.

See [QUALITY-LEDGER](QUALITY-LEDGER.md) and [#568](https://github.com/gamesbyian/Chunks/issues/568) for exact evidence and pending gates.
## Transfer-level archive deletion after verified extraction (owner clarification, 2026-10-27)

Offer **Delete archive after extraction** in individual transfer details and alongside **Remove transfer** / **Remove transfer & data**, as well as the existing cleanup wizard. This is a separate, unchecked, user-confirmed operation. Eligibility requires a verified completed extraction manifest mapping exact source archive to independently retained output files, readback/size/hash evidence where possible, accessible outputs, reference/ownership safety and current engine status. A matching name alone cannot qualify. Surface exact archives/outputs, estimated unique reclaim and explicit warning that deleting torrent-backed archive data normally invalidates torrent pieces and seeding. Explicitly acknowledge this loss independently of the torrent/session remove action; never treat extraction as automatic authorization to delete originals. Remote archive deletion requires a verified scoped remote filesystem adapter, not merely rTorrent XML-RPC. All destructive actions remain dry-run/preflight/journal/postcondition gated; if evidence missing, offer inspection or refuse. **Requirement only.**

## User outcomes and defaults

1. Set an optional **on-device Chunks storage cap** per volume/Place, inspect used/remaining/free, receive understandable tiered warnings and avoid filling the device. There is no automatic deletion of source data to enforce the cap.
2. See what can actually be reclaimed, distinguish removable Chunks-managed independent files from active seeding dependencies, and use a compact **cleanup wizard**. Batch review is possible but never conceals destructive consequences.
3. Extract a completed archive immediately or opt into extraction when its constituent download files are verified complete. Source archives remain intact by default even if successfully extracted. Extracted files are independently managed and never silently substituted for seeding data.
4. See explicit, factual consequences **in the review screen before approving** any choice that removes bytes relied upon by one or more torrents. A missing archive will usually make affected torrent pieces unavailable and prevent valid complete seeding, even when extracted media exists elsewhere.
5. Keep local/remote semantics honest. Android device storage is not server storage. rTorrent RPC can remove a session, but remote payload deletion/extraction needs separately authorized verified filesystem operations.

## Storage accounting and quotas

- A budget is scoped by physical volume, SAF tree/root or engine-accessible Place identity, **never by visible directory label alone**. Show user-selected cap, actual file allocation where measurable, logical expected payload length, known remaining torrent bytes, Android-reported free bytes, reservations and anticipated peak extraction space; mark unknown estimates as unknown rather than conflating logical size with blocks allocated. Measure caches, partial files, staging, extracted output, independent library copies separately.
- Count physical objects once even if multiple transfers, Collections, paths or published views point to them; account for hardlinks, shared references, sparse files and deduplication uncertainty. If actual released blocks cannot be established, show **potentially reclaimable** rather than promised freed bytes.
- Proposed starter defaults, adjustable: warn at **70%, 85% and 95%** of the selected cap, with hysteresis, deduplication and persistent status in app; also surface device low-space signals regardless of cap. No push notification spam or repeated alert every polling interval. No default user-defined cap is imposed without consent; OS safety guard still applies.
- Show at Add and before extraction a forecast of target-volume headroom and estimated peak usage; the app should offer choosing another Place, stopping selected downloads, or adjusting cap when needed.
- **Local engine**: the merged #174 app-folder cap is **advisory only**: explicitly saved/cleared on this device, calculated from bounded complete logical folder surveys, with no automatic enforcement, deletion, notification, or suspension of seeding. Actual protected write limiting remains to be built. Reserve usable headroom and safely pause affected new/in-progress *downloads* when projected writes threaten a future enforced cap or OS low-space floor; preserve existing completed seeding/upload paths, and require explicit resume/override. A hard numerical guarantee demands independent on-device enforcement testing under concurrent writes, sparse allocation, background lifecycle and app death. Do not claim one now.
- **Remote engine**: display reported capacity only if server/provider supplies reliable scope and timestamps. Cap defaults to **advisory**; enforce via server-backed limits only if proven. Phone cap must not pause a remote seedbox download. Where capacity cannot be obtained show 'Storage capacity unavailable'.
- Quota changes must not silently erase data already over cap. Explain that new writes are restricted while users choose a remedy. For impossible or stale measurement, warn without fabricating a precise cap status.

## Cleanup wizard

Entry points: storage dashboard, low-space warning, transfer file details and Places. Steps:
1. **Scope:** local volume or explicitly selected remote Place. Show fresh inventory time, stale/unavailable state and breakdown of backing files, independent library copies, extracted outputs, temporary/staged files, and unknown ownership.
2. **Find space:** default filter **Safe for sharing**; alternative **Include items that affect sharing**. Candidates sorted by verified recoverable bytes, age, access, ratio/seed health and source relationships. Distinguish 0-byte recovery for shared/hardlinked files and non-owned files.
3. **Review exact targets:** identify Transfer/engine and infohash/file index, visible title and actual storage path. For every selected action show what remains, what stops sharing, other references, how much space might be released, and whether recovery is possible. Separate 'Remove from Chunks/rTorrent session (keep data)', 'Delete backing data', 'Delete extracted result', 'Delete independent published copy', and 'Discard temporary files'. Unowned files cannot be included merely by directory proximity.
4. **Confirm:** a meaningful warning and separate explicit approval for any seeding-affecting deletion. Sample: **'This archive is part of a torrent. Deleting it will make affected pieces unavailable for sharing. Your extracted files will remain. To seed the full torrent again, restore or re-download its original bytes.'** Do not replace with generic 'Are you sure?'. Summarize multi-torrent impact on batch review. Offer cancel and preserve originals.
5. **Execute and reconcile:** capability/ownership/reference recheck; durable journal/staging as supported; accurate pending, deleting, verified, partial, uncertain, and recoverable/irreversible statuses. No blind retry after an ambiguous response. Report verified released space, not merely predicted savings. Do not promise undo without an actual Trash or recovery implementation.

No automatic recommendation executes a destructive mutation. Never follow symlinks, delete outside approved scoped roots, assume exclusive ownership, or delete while torrent mapping/write operations are uncertain. A shared physical file may block deletion even if one Transfer appears stopped. Native Android SAF deletion and remote assisted FS mutation have different permission/recovery gates.

**Specialized extension:** nested archive budgets, encrypted inputs, independent SFV/SHA inspection, hardlink/reflink awareness, remote namespace path mapping and verified cross-seed reuse are detailed in [FILES-PROTOCOL-AND-DIAGNOSTICS](FILES-PROTOCOL-AND-DIAGNOSTICS.md). This cross-reference does not expand initial ZIP implementation, change extraction's default-off policy or relax deletion requirements.

## Archive extraction experience

- Per-completed-archive action **Extract now** and simple **Auto-extract when ready** switch in transfer details. Future-rule settings may apply to an explicitly approved Place/category, disabled by default, independent of organization classifier confidence. The per-transfer toggle may optionally apply to *this transfer only*. An obvious settings screen can inspect/revoke approved auto rules.
- Destination: choose original containing directory when permitted, separate local folder or independent library Place. No remote archive extraction via rTorrent RPC alone; if source is remote, require safe authorized remote filesystem provider or an explicit download-to-device workflow with its own storage forecast.
- Extract on verification of all source bytes required by that archive set. For incomplete multipart groups, pending pieces, bad CRC or unstable I/O, explain waiting/failure. Multiple archives in one torrent may each become eligible independently. Do not assume a torrent's single 'completed' flag alone validates archive group integrity.
- Support formats incrementally after evaluating library security, maintenance, licenses and Android integration. ZIP is initial target; 7z, RAR, multipart and encrypted archive compatibility are separate tested capabilities. If a password is needed request it interactively, never silently store it. Avoid retry storms for permanently unsupported formats.
- Preview archive contents, file count and known expanded size, destination and worst-case temporary staging demand; when unknown show uncertainty and apply bounded streaming limits. Users can choose collision policy **skip, rename, or explicit overwrite** with preview; no silent replace. Keep originals by default. Extracted files become provenance-linked independent artifacts with own deletion rules.
- Use bounded streaming extraction, check **actual** accumulated decompressed bytes, ratio, count, depth, member names, traversal, absolute paths, Unicode/case collisions, symlinks/hardlinks, special files and zip bombs. Normalize and constrain via handles/SAF scope; declared header lengths alone do not establish safety. Limit concurrent jobs; cancel/cleanup partial output safely; survive process death with idempotent operation IDs and reconciliation to avoid duplicate output.
- On-screen status: waiting for verified bytes; estimating; requires password; unsupported format; extracting (progress); verifying; complete/open result; failed/retry; partial/recovery. Accessibility: 48dp targets, TalkBack-specific description of consequences, 200% text, no status conveyed by colour alone.

## Read-only actual ZIP inventory candidate (2026-10-24)

`ZipArchiveInventory` adds a bounded central-directory scan for an explicitly staged **local `File`**, converting actual ZIP headers to the conservative `ZipEntryPreflight` model. It reads no member payload, writes no extracted files, retains source bytes and returns a blocked result for malformed archives, permission errors, excessive staged input size or unsafe paths/metadata. A small deterministic corpus exercises **real** ZIP bytes, traversal records, Unicode/case collisions and compressible-content ratios. The default staged-input cap is currently 256 MiB and must be revisited for practical large archives, Zip64 and actual Android storage budgets.

This work has **not** implemented URI/SAF import, encrypted/multipart compatibility, symlink/executable special member detection, safe output handles, streaming actual-byte limits, recovery, collision handling, extraction UI or automatic extraction. Never treat `BOUNDED_STREAM_CHECK_REQUIRED` as permission to write. An archive with apparently safe central-directory metadata can still be malicious when decompressed. ## Warning hysteresis model (merged policy; Android delivery pending)

`StorageWarningHysteresis` is a pure Kotlin decision function for one *optional* per-volume cap. It emits a new in-app advisory only upon crossing a higher 70%, 85%, 95% or over-cap band. Previously emitted bands remain latched until usage drops at least five percentage points below the band's boundary. Unknown allocation preserves the latch and never becomes zero; disabling a voluntary cap resets it. Deterministic tests exercise oscillation, tiny and extreme byte counts, stale readings and cap changes. This model sends no notifications and stores no state. **Actual settings persistence, volume identity, OS low-storage integration and user-facing warning delivery are not implemented** and remain separately gated under #70.

## Manual ZIP extraction executor (model slice, 2026-10-25)

`ZipExtractor` is the first *writing* S2 component. It is platform-neutral: callers supply a `ZipExtractionTarget` (an approved Android SAF tree in the app, a plain directory in JVM tests) and an app-private `ZipExtractionJournal`. Sequence:

1. Re-run the full read-only `ZipPayloadVerifier` pass on the app-private staged copy; any refusal writes nothing.
2. Headroom: verified output bytes plus a reserve (max 16 MiB or 5%) must fit the destination's reported free space. Unknown free space is refused unless the caller passes an explicit user acknowledgement.
3. Write-ahead journal `BEGIN`, then every `DIR`/`FILE` line is durably appended **before** that entry is created.
4. Members are streamed into a new randomly named `.chunks-partial-<operation>` folder, re-checking actual bytes, cumulative budget, expansion ratio, declared size and CRC while writing. Providers that refuse or substitute a name fail closed.
5. Publication is a single non-replacing rename of the partial folder to a **new** folder named after the archive (`Name`, `Name (2)`, …), confirmed by readback.

Collision policy for this slice: extraction **always** creates a new folder; it never merges into, opens for writing, replaces or deletes any pre-existing file or folder. Per-file skip/rename/overwrite inside an existing folder is not offered. Cancellation and failures remove only journaled entries of the operation's own partial folder, deepest first, non-recursively; anything unexpected (e.g. an unjournaled file) leaves the partial folder in place as `NEEDS_ATTENTION`. `reconcile` resolves an unfinished journal after process death without retrying: it recognizes a completed rename, or rolls back. The source archive is only read.

Evidence class: JVM tests with real ZIP bytes and fault injection (provider refusal, write failure, cancellation, simulated process death before and after publish). Android SAF target, extraction UI, physical-device behaviour and auto-extraction remain unbuilt/unproven.

## Android manual extraction journey (SAF slice)

After a local ZIP review verifies, the Local ZIP screen offers **Choose where to extract…** (Android `OpenDocumentTree`). A review step names the archive, destination, new folder name, file count, output bytes and free space. Free space is known only for primary shared storage (`StatFs`); for other providers the user must tick an explicit acknowledgement or extraction is refused. Insufficient space disables the action. The archive is re-staged privately, then `ZipExtractor` writes through `SafZipExtractionTarget`, which reads back every created/renamed document name and treats provider-substituted names (`x (1)`) as refusals, and refuses to delete non-empty directories because SAF deletes recurse. Cancel is available while running. Journals live in app-private `files/zip-extractions/`; on the next visit, unfinished journals of operations not running in this process are reconciled (completed publish recognised, otherwise journaled entries rolled back), never re-extracted. The tree grant is persisted for recovery and released once no journal needs it.

Evidence class: debug-only `FixtureDocumentsProvider` (a disposable app-private DocumentsProvider that, like the platform provider, silently picks unique names) exercised through real ContentResolver/DocumentsContract calls on an API 35 emulator. Vendor providers, SD cards, cloud providers, the system picker journey itself, physical devices and process-kill tests on device remain unproven. Auto-extraction remains disabled.

## Completion gates after the initial SAF prototype (2026-10-26)

1. Real primary storage/SD/cloud SAF provider and complete picker-to-result tests: provider-selected names, collision refusal, revoked permission, slow streams, low capacity, cancel and physical process kill at every publish/recovery stage. A debug-only DocumentsProvider test is insufficient.
2. Persistent cap per actual volume with measured or explicitly unknown allocation, shared/hardlink reference graph and 70/85/95% deduplicated warnings. Enforce only after libtorrent write-path and Android race proof; preserve seeding and never delete on crossing a cap.
3. Interactive safe-first cleanup preview with exact transfer ownership, physical reclaim confidence and warning for torrent-backed archives. Every real deletion requires permission, preflight revalidation, independent journal/fault injection and truthful post-delete/seed readback. Extraction **never** authorizes deleting the source.
4. Opt-in auto-extraction only for a verified complete supported archive and approved destination, after cancellation, deduplicated event/restart, actual byte limits and source-retention acceptance; no implied support for encrypted/multipart/RAR/7z.

## Fail-closed post-write verification and bounded library publication (2026-10-26)

Merged #163 rejects independent SAF library-copy publication when a torrent contains more than 10,000 non-padding files: a 10,001-entry probe makes a potentially truncated source inventory explicit. Copying only the first 10,000 rows would misleadingly publish an incomplete library. Complete paging for larger transfers remains future work.

Merged #164 adds **read-back of destination bytes** before any SAF ZIP extraction/library-copy folder is published. For ZIP it checks actual stored size and CRC; for independently copied torrent files it checks actual stored size and SHA-256 as well as the source's post-copy digest. A provider that writes bytes but later refuses the read, truncates or corrupts them must fail closed through journaled rollback. Tests exercise such provider faults in JVM target abstractions and Android source compilation. This does **not** establish physical/provider-specific durability, actual Android process-death recovery or that a provider cannot mutate bytes again after verification. More evidence is required before automated extraction or cleanup of backing data.
