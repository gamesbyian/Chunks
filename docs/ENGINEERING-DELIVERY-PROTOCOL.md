# Engineering delivery protocol: learn from the Chunks PR/issue archive

**Authority:** operational practice under [AGENTS](../AGENTS.md), the [documentation standard](DOCUMENTATION-STANDARD.md), [CI policy](CI-POLICY.md), [requirements-rationality audit](REQUIREMENTS-RATIONALITY-AUDIT-2026-10-31.md), and the **one active** [work queue](WORK-QUEUE.md). This is **not another queue, product contract, or permission to disable a defect safeguard**. Current facts come from live main/issues/PRs, not this dated review.

## Deliver related environments and dependent features together

For every planned local/remote feature, check whether a *shared behavior with distinct execution adapters* can be delivered as one scoped vertical feature. Capture the common intent, selected environment, authority/capability, confirmation, preconditions, observed postcondition, retry/uncertainty and accessibility contract. Then build local and remote execution seams concurrently where independent, rather than completing phone-specific product/UI work before considering rTorrent. Do not unify incompatible transport or filesystem guarantees, and keep destructive features fail-closed until positive file-ownership and readback proof.

Create a shared acceptance scenario manifest with per-adapter fixtures/observations. Run both in a coordinated session, using one built APK/emulator boot, shared test assets and disposable servers when possible. Each adapter retains independent pass/fail receipts, adversarial tests and rerun selection. Rerun only genuinely affected gates, plus one cross-environment installed UI/identity check at integration; reuse successful unaffected owner/device evidence. A combined session is a **resource scheduling optimization**, never permission to declare a missing/skipped/failed subcase green.

Perform a second *capability-family scan* before new features: media identity powers metadata, Similar Transfers, search and smart rename; shared transfer inventory powers combined list, details and remote observations; destination and identity safeguards apply to Add, Move and Remove but do not automatically authorize all three. Separate safe shared modeling from dangerous attempts to universalize low-level providers.

## The measurable objective

Maximize **correct, usable, integrated user journeys per unit of engineering and CI effort**, without sacrificing data integrity, account isolation, security, accessibility or owner-approved capabilities. Every PR must either (a) repair an observed harmful failure, (b) complete a working slice of a required journey, or (c) remove a specific test/architecture blocker on the shortest path to (a)/(b). Generic hardening/research needs a concrete risk or decision it will resolve.

Anchor active development to end-to-end paths: phone .torrent/magnet/Share → verified default or chosen Place → Add/Start/piece progress/Stop/recheck/restore/seed; rTorrent authenticated exact instance → inventory → Add/Start/Stop/priority/session-only Remove → observed readback; combined environments → truthful scope, controls, errors and accessibility. Include **positive execution** as well as destructive/ambiguous negative controls. A green component harness with no production caller is useful research, not feature completion.

## Real transfer evidence is the primary acceptance standard (owner mandate 2026-11-01)

Use [REAL-TRANSFER-ACCEPTANCE](REAL-TRANSFER-ACCEPTANCE.md) before claiming any ordinary torrent user journey is complete. Real `.torrent` metainfo, real metadata-resolving magnets, real servers and peers, exact-job verified-byte progress, and actual installed UI paths outrank test doubles. Keep mocks and simulated hostile inputs as quick **secondary** diagnostics, not proof of a working feature. No amount of mocks replaces a working Add → peer bytes → Stop → Start → Remove, and a synthetic magnet that cannot obtain metadata does not prove magnet support. Record separately disposable-server, protected-host, installed-emulator and physical-handset results.

For ordinary rTorrent and local BitTorrent behavior, begin by comparing ruTorrent/Transdroid and documented rTorrent/libtorrent primitives. If Chunks issues a different operation sequence, explain and test the difference on actual engines before inventing custom state machinery. Treat the owner's paused-Add discovery (#4/#973) as a process regression: its old simulated/active-only receipts were insufficient despite passing. A corrected shipping path needs an old-code-failing real regression and independently verified user-path acceptance.

## Before coding: six-line execution card

Put this in the owning issue or PR, **not copied into new standalone planning documents**:

1. **Outcome:** which normal user journey becomes more reliable, usable or verifiable?
2. **Evidence:** exact current main SHA, confirmed bug/test or specific credible failure with threat/impact; distinguish observed, hypothesized and policy-only.
3. **Authority / scope:** actual user authorization, exact profile/hash/Place/provider/Android tier; conventional upstream and platform behavior; conflicting historical rules superseded.
4. **Smallest intervention:** change the existing canonical code path first; say whether the route is shipping production, test fixture, or dormant research. No parallel replacement subsystem without a demonstrated missing capability.
5. **Proof:** one positive end-to-end case, targeted negative/failure recovery, exact-head CI and separate physical/host acceptance if required. Use real outcome/readback, not a proxy callback or declared capability.
6. **Exit:** merge/close disposition, remaining blocked acceptance, what the next agent can execute immediately, and what the change does **not** prove.

If there is no production caller and no identified next integration task, **research cannot be marked P0 complete**. Research is valid to answer a bounded question, and its useful tests remain preserved.

## Risk, priority and release gates

- **Global stop:** demonstrable reachable unintended data loss, path escape, credentials/account cross-target mutation, uncontained destructive operation or a required product CI failure at the current head. Stop unsafe **affected** operations and fix promptly.
- **Capability-local stop:** a proven unsafe optional ZIP/library/SAF/provider action stays refused until repaired and positive/negative tested. While unreachable/disabled, it blocks **that feature's** release, not automatically a basic phone/rTorrent daily-use candidate. Preserve the feature as required future work with an honest UI state; never label it implemented.
- **Acceptance limitation:** emulator versus handset, disposable versus protected server, and provider-specific behavior affect claims about those environments, not unrelated proven journeys. Record a release-feature matrix rather than letting one missing handset or rare provider prevent all engineering progress.
- **Hardening/research:** unmeasured memory growth, speculative races, exotic variants and uninstalled custom engines must carry an observable failure threshold and explicit go/no-go decision. Raise priority when evidence establishes impact; do not give them default universal G0 status.
- **Two-iteration reset:** after two unsuccessful revisions (or one substantial design expansion) without a new shipping positive-path receipt, revisit the premise and the simplest built-in solution **before** extending the stack. This is a review trigger, not authorization to ignore a bug or abandon the feature.
- **Never reduce safety silently:** staged release, provider limitation or a deliberately refused optional operation must be documented; preserve user-visible feature commitments and return to them once dependencies qualify.

## Branches, reviews and CI

- Prefer **one integration branch per executable vertical slice**, based on current main; at most one directly stacked follow-up pending integration unless an explicit dependency and integration owner justify more. Parallel agents own disjoint source seams. Review final diffs against main, not merely against the parent research branch.
- No independent branch for a new hypothetical invariant until it has passed the rationality test; no growing C++/Kotlin architecture merely because each isolated component passes fixtures.
- Test order: fast deterministic model/fixture → real scoped adapter/Android build → exact integrated-head relevant workflow → explicitly authorized physical/host tier. Select **fewest workflows that cover changed risk**, and use concurrency cancellation for obsolete source heads. Keep path-scoped docs and font-lab checks lightweight.
- A red result gets phase triage. If a harness/boot failure, preserve its red status as *unexecuted product proof*, correct/retry the failing tier and do not claim either product failure or success. If a real behavioral assertion failed, fix it before merge. Check the final merged main head when integration changed source.
- Independent security/storage review checks user intent, target identity, rollback/cleanup, preservation under read failure, positive user action and exact source, not an unlimited inventory of speculative attacker interleavings detached from the threat model.
- Keep issue status, [SPEC-COVERAGE](SPEC-COVERAGE.md) and [QUALITY-LEDGER](QUALITY-LEDGER.md) updated **once at integration/meaningful evidence transitions**. Dated research notes are evidence; they must never supply executable priority.
