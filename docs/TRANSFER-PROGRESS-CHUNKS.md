# Recency-preserving transfer progress chunks

**Status:** owner-approved visual/interaction requirement, **planned; not evidence of implementation** (2026-11-03). Normative product intent: [PRODUCT](PRODUCT.md); interaction/accessibility: [UX](UX.md). This focused document specifies the rendering and state algorithm. It is **post-P0 UI refinement** unless an actual daily-use regression makes basic transfer progress misleading or inaccessible.

## Outcome

Across phone-local, each rTorrent profile, Combined transfers, expanded details and optionally per-transfer widgets, progress starts as an **empty horizontal bar** and accumulates contiguous, proportional **visible segments when verified observed completed bytes increase**. Do not pre-render hypothetical segment slots, recolour a full prepartitioned ruler, or suggest that a segment maps to a torrent piece or physical file region. The bar communicates *how much completed content was observed between observations*, in chronological order; it is not a BitTorrent piece availability map. Keep ordinary numeric percentage, verified-completion semantics and textual transfer status independent from the decorative segment history.

## Default rules

1. **Zero and progression:** At zero verified completion show an empty track. On a new positive progress observation append a new segment sized by the delta in normalized verified completion (0..1) relative to the preceding accepted observation. Segment widths are fractions of the total content width; sum of visible widths equals current observed completion. Do not add a segment for an unchanged poll, UI recomposition, list scroll, rotation, view re-entry or status-only refresh. Record observation events once at a stable transfer scope: environment/profile + exact hash.
2. **Bounded, recency-preserving history:** Default maximum **20 visible segments** per bar. Preserve the **most recent 8** distinct qualifying increments when possible; progressively coalesce **oldest adjacent segments** into wider historic bands first. Never reorder or discard completed area. When the 20-segment cap is reached, merge the oldest eligible adjacent pair before appending the new recent segment; if there are fewer than 8 historic entries, straightforward oldest-first merging still applies. A segment represents its summed underlying delta after merging. Avoid the earlier alternative that merges the globally smallest adjacent pair regardless of age: recent detail is the design priority.
3. **Tiny deltas and narrow views:** Accumulate positive increases below a view-dependent visible minimum (initial target **3 physical pixels**, evaluated against the actual available track width and pixel density), and display their completed area accurately without creating many hairline segment borders. Commit the aggregate as one new event once it meets the threshold; use a stable aggregation policy unaffected by a change in refresh cadence. A 100% complete bar must fill the track precisely, including the final small increment. Implementations may reduce the effective cap responsively when gaps would consume an excessive fraction of a compact track.
4. **Separation and colour:** Use thin, restrained inter-segment separators and subtle alternating tones without encoding unsupported piece states, stalls, quality or rates. Keep environments identified separately by accessible name/text and colour. Separators must not subtract visible completed fraction or make a fully completed download look incomplete. High contrast, colour-vision differences and dark/light theme must remain usable; the entire pattern is supplementary to percentage/status text.
5. **Persistence and reconstruction:** Preserve the observation history across list recycling, configuration change, backgrounding and ordinary app relaunch when feasible; persist compact, bounded per-transfer state keyed to the verified environment+hash, not a global hash alone. When no history exists (e.g., first sync with a remote job already at 65%), show a **single 65% baseline segment** rather than fabricate historical increments. Resume capturing real subsequent progress. Cold reconnect, offline and uncertain readings never invent chunks. A stable old baseline is preferable to resetting to empty on each remote refresh.
6. **Corrections:** If a trustworthy engine recheck reduces verified completion, reconcile the right edge to the lower accurate total, trimming/removing newest history as necessary, and explain the recheck/status in normal UI. Never preserve a visually full bar against a lower authoritative completion. Ignore transient stale or out-of-order snapshots until ordered/freshness checks settle; do not animate backward and forward on polling races. If data is unknown, show an explicit unknown/offline state rather than asserting zero completion.
7. **Motion/performance:** Progress geometry may animate briefly when allowed, but reduced-motion renders the updated state immediately. No per-refresh recomposition of entire lists, no unbounded samples, no network polling solely for decoration and no persistence write per paint frame. Use shared progress rendering logic for local/remote/combined, not divergent engine-specific appearance.

## Acceptance scenarios (batch with ordinary UI visual testing)

- 0 -> 8 -> 8 -> 13 -> 28% yields **three** proportional chunks (8, 5, 15), not four or a predefined grid. On first observing an existing transfer at 60%, show one 60% baseline band; +4% adds a 4% recent chunk.
- After more than 20 qualifying increments, visible bands remain <=20, newest 8 increments remain distinguishable where track width allows, older bands are merged chronologically; lengths still sum to the observed percent (within rendering precision).
- Many 0.01% observations do not create hairline segments. Final 99.99 -> 100% fills all remaining available space. Resizing recomputes pixels from proportions, not a historical pixel layout.
- A real recheck from 75% to 70% trims newer/rightmost completion, while stable/stale/offline refreshes do not create chunks. A reconnect and a list scroll do not change the segment count when progress has not advanced.
- Phone and two remote profiles with the same infohash retain **separate histories**; Combined mode uses those same records, not a new timeline. On a cold first observation the numeric percent and bar agree without invented intermediate samples.
- Verify contrast, TalkBack (accessible label contains percent and status; no reading individual decorative chunks), reduced motion, Pixel 6 Pro compact collapsed rows, expanded detail and theme variants. Batch screenshots/functional checks with the next UI lane; avoid adding this as an independent P0 gate.

## Engineering scope and scheduling

Implement as one reusable bounded progression model/renderer used by relevant transfer surfaces. Prefer a small persisted event/coalesced-band record; do not store infinite per-poll data. Review current UI and model ownership before implementing. This requirement is accepted but **not shipped or visually qualified** by documentation alone. Track alongside the existing UI/UX improvements rather than spawning local and remote implementation campaigns. Changes to the progress display must not alter transfer engine state, network behaviour or verified progress calculations.
