# Files, swarm controls, diagnostics and network privacy

> **Authority:** feature-level contract for high-safety file, protocol and diagnostic details inadequately pinned down in the ecosystem comparison. Read with [PRODUCT](PRODUCT.md), [STORAGE-AND-EXTRACTION](STORAGE-AND-EXTRACTION.md), [TRANSFER-FILE-RECOVERY](TRANSFER-FILE-RECOVERY.md), [EXTERNAL-FILE-ACCESS](EXTERNAL-FILE-ACCESS.md), [SECURITY](SECURITY.md) and [CREATE-AND-SHARE](CREATE-AND-SHARE.md). **Status: planned specification, not evidence of implementation.** Fxx.yy IDs refer to [research PR #537](https://github.com/gamesbyian/Chunks/pull/537).

## Scope, exclusions and identity

This contract resolves **27** items: F03.12/13/14/20/24; F04.08/09/10/11/12/14/15/21; F08.07/10/11/12/13; F09.02; F13.01/02/03/09/10/14; F15.07/15.15.

A locally running Arvid libtorrent session and a separately administered rTorrent session are distinct implementations. Chunks offers one shared presentation with exact environment scope, exposes advanced controls only on verified supported backends and never implies server filesystem privileges from torrent RPC. Engine defaults are authoritative for transport/piece algorithms unless a safe, independently tested override exists. A read-only visualization or a saved preference cannot itself prove that a command was applied.

**Immutable torrent metadata**, **engine file index and backing-path mapping**, **real filesystem object**, **Chunks display alias** and **published library copy** retain separate identities. Physical file and link operations must follow the existing journal, permissions, exact target and no-silent-data-loss invariants.

## Storage, archive and mapping edges

- **F03.12 nested/encrypted archives:** The existing extraction wizard's trust model applies recursively to nested archives and all requested formats. Show a *per-level* plan with archive type, depth, declared/observed size, estimated free space, password need, encrypted member limitations, destination and original archive retention. Passwords are entered at execution time, never logged or persisted by default; no brute-force password feature. Each nested extraction counts toward a *shared* global member/depth/byte/time/ratio budget, not a fresh budget at every level. Unsupported format/encryption is explicitly refused; archive success never authorizes removal of seedable source bytes. All extraction remains opt-in.
- **F03.13 independent checksum and metadata inspection:** Offer **Inspect checksums** for permitted accessible files: SHA-256 and size by default; optional SFV/CRC and legacy hashes labelled non-cryptographic or weak when relevant. Parse NFO/info/text and archive manifests as inert bounded content, not executable instructions. A sidecar checksum can be untrusted; report *matches supplied checksum* separately from *BitTorrent piece-verified* and *verified on remote storage*. Large remote reads require an independent authenticated byte-access adapter, cancellation, progress and network estimate.
- **F03.14 cross-file pieces and layout:** Creation and verification must correctly handle pieces spanning file boundaries (including empty files and boundary offsets); selective skipped files can still require neighboring piece bytes. Explain when file completion is waiting on shared boundary pieces. Alignment flags are immutable torrent-creation choices, never retroactively rewritten in an active torrent. Existing metainfo and file priority must remain valid for mixed v1/v2/hybrid metadata; claim support only for actually tested versions.
- **F03.20 shared backing/link detection:** File operations and cleanup previews identify hardlink inode sharing, symlink targets, reflink/copy-on-write uncertainty and cross-seed shared data when the authorized filesystem API can verify them. A shared inode may survive one path deletion; deleting the last linked file or overwriting shared bytes may break multiple jobs. Unknown link provenance blocks automatic reclaim estimates and any unreviewed destructive action. SAF and remote protocols may not expose inode/link data, so label **unknown**, never **unshared**.
- **F03.24 remote path translation:** Define explicit, editable mapping between the engine's reported path namespace, externally accessed SFTP/FTP/WebDAV paths, containers, chroots, mount points and user's Places. A rule is per exact server/profile and root, bidirectional only when verified, and includes normalization/case/Unicode policy, traversal protection and a test-read proof. Never globally replace substring paths, resolve outside an authorized root, or assume '/downloads' in two containers names the same bytes. Revocation/volume change invalidates mapping; a failed map offers diagnostics without mutating the torrent.
- **F15.07 piece-aligned creation:** In expert Create & Share, optionally offer a piece-alignment choice *only where a tested creator can guarantee standard-compliant output*, with a plain warning about padding/compatibility and potential changed torrent hash. Default follows the verified interoperable builder, not a specialist optimization. Test zero-size, cross-file boundaries and both seeding peers; don't change an existing torrent's identity.
- **F15.15 data-preserving cross-seed reuse:** An optional assisted workflow may propose additional torrent *jobs* referencing verified identical backing bytes across tracker metadata, but does not silently overwrite originals, use unverified symlink/hardlink layouts or share private tracker metainfo. Match sizes, actual hashes/pieces, file indexes and authorization; human confirmation required before creating link/renamed views or new jobs. Account for different v1/v2 layouts, incomplete files, same-title-different-bytes and independently enforced tracker obligations. Remove/cleanup must detect all references first. This feature is distinct from job-only cross-engine Copy/Move and normal in-place data recovery.

## Collection-wide file metadata search and batch selection

**Discovery across transfers:** A user can inspect indexed torrent file entries across the currently selected authorized transfer environments with filters for filename/extension, known size, file priority and owner transfer. Prefer bounded, paged/virtualized, cancel-safe read-only metadata queries with each row carrying the exact environment, torrent identity, file index and observation freshness. Distinguish engine file entries from actual filesystem objects and published library copies; do not infer disk existence or openability from torrent metadata. A remote rTorrent adapter may be capable of file-list inspection without SFTP/byte-read capability. Unknown file attributes are labelled unknown and not silently filtered as false. Partial profile results are explicitly reported.

**Mutation boundary:** After a user selects multiple results, preview affected exact jobs/files, cross-file piece dependencies, permissions, backend support and any changes to seeding. Execute only individually verified applicable actions, reporting per-item refused, pending, uncertain and verified outcomes. Changes to priority can change what pieces are fetched; they do not authorize renaming, moving, deleting, zeroing or adopting physical bytes. Re-read file-index identity and capability before each mutation; a stale selection is not permission to target a different item/server. Existing storage/transfer job boundaries remain authoritative.

**UI owner:** The contextual file-finding and list/search handoff design is specified in [UX](UX.md#findability-and-truthful-outcomes-in-everyday-torrent-journeys-binding-ux-research-informed-2026-10-30). This is planned capability; no collection-wide search or cross-backend batch proof is claimed by this document.

## Native protocol and peer controls

- **F04.08 transport and port capabilities:** Report TCP, µTP/UDP, IPv4/v6, UPnP/NAT-PMP and any hole punching as *supported/configured/observed* distinct statuses. Local listening settings require explicit consent, safe platform privileges and network-interface attribution. Do not infer remote listen state from the Android client IP or HTTPS RPC port. A carrier-grade NAT or firewall may prevent inbound peers despite a successful port-binding call.
- **F04.09 encryption and tracker trust:** Expose engine-supported BitTorrent peer encryption preferences with accurate semantics (allow/prefer/require when actually implemented). Do not call BitTorrent protocol encryption anonymity; private trackers and HTTPS announce TLS require separate trust and certificate validation. Never allow globally insecure TLS as a compatibility fallback.
- **F04.10 peers, slots and connection limits:** Advanced per-environment connection slots, timeout and upload-slot controls are shown only with meaningful capability and range; otherwise diagnostics remain read-only. Distinguish active socket peers, tracker-reported peers and global backend limits. Test no accidental throttling of seeding on new profiles when defaults are inherited.
- **F04.11 peer management:** Advanced manually add peer, kick, ban, allow/deny rules are guarded by exact session+peer identity, permissions and engine capability. UI must differentiate one-time disconnect, ephemeral ban and persistent block. Never silently ban all peers sharing a country or client string; an arbitrary untrusted peer list isn't an authorization to contact hosts.
- **F04.12 peer filtering/proxy metadata:** IP blocklists and peer class filters are opt-in local-engine capabilities or independently verified server-native settings. Show last update, source authenticity, size, effect and undo; geolocation is coarse/inexact, not proof of jurisdiction or maliciousness. Client-fingerprint filters may be deceptive and must not be framed as security guarantees. No cross-environment application without explicit target.
- **F04.14 piece-map diagnostic:** Offer an optional scalable piece/payload map with downloaded, verified, requested, availability/unknown and skipped/shared-boundary state visually distinct. Bounded sampling is acceptable with a legend and resolution disclosure; do not render one UI node per piece on huge torrents. An unavailable remote piece API produces an honest unsupported state.
- **F04.15 request algorithm:** Rarest-first, endgame and playback/ordered piece demand are engine-owned algorithms. Chunks can offer a safe explicit mode only when independently testable and can revert; do not claim support just because file priority changed. Warn that aggressive sequential requests can reduce swarm efficiency and that no piece scheduling can fetch absent pieces. Link to [Finish in Order](PRODUCT.md#multi-file-completion-order-finish-in-order-owner-direction-2026-10-27).
- **F04.21 disk I/O controls:** Expose advanced allocation/cache/file-descriptor/IO controls only if the engine surfaces validated writable settings. Prefer safe defaults; show storage impacts and reset/restart requirements. Reject unsupported device/provider combinations; do not interpret an OS cache as durable on-disk bytes. Never risk random-access safety or verification to create a benchmark result.

## Connection/privacy model

- **F13.01 separate proxy paths:** Distinguish **peer traffic**, **tracker announces**, **magnet/metainfo URL retrieval**, **indexer/feed lookup**, **artwork enrichment** and **remote-control HTTPS**. These may take different routes and carry different credentials. Settings list which traffic classes each configured proxy actually covers, with a test method and no blanket 'anonymous' claim.
- **F13.02 proxy families:** SOCKS4/5, HTTP(S) proxy, Tor-assisted *web* fetch and I2P-style routes are separate opt-in adapters only where a tested library and network stack support them. Do not claim Tor makes ordinary TCP/UDP BitTorrent peer traffic anonymous. Unsupported routes must fail visibly, never silently fall back to direct public traffic if user configured **proxy required**.
- **F13.03 VPN binding/kill behavior:** When **VPN required** is selected for the phone engine, require verified local interface routing/binding and automatic hold on VPN disconnect/rotation; warn if Android/libtorrent cannot guarantee leak prevention on the target OS. Remote server VPN is unrelated; the phone may not manage or certify it. UI exposes last tested route/interface and ongoing uncertainty without displaying a fictitious privacy seal.
- **F13.09 ban/block policy:** Peer-block lists are per exact engine and only enforced where that backend exposes proven application and readback. Disclose false positives, expiration, manual overrides and differing effectiveness against DHT, trackers, indexers and already connected peers.
- **F13.10 isolation:** Never carry private tracker announce URIs, proxy credentials, bind interfaces, rules or derived peer identities between phone and remote server profiles implicitly. Cross-profile presets require opt-in and per-target capability/security preview; one profile's unlocked UI does not grant another profile's auth/lock privileges. No claim of hardware/container-grade network isolation from Chunks UI alone.
- **F13.14 audit and recovery:** All sensitive or mutation-capable actions produce local bounded, redacted event records with target profile/transfer ID, requested versus verified outcome, provenance, undo/recovery if possible, and retention. Export is explicit and redact-by-default; no collection on a developer-owned server. Log contents cannot authorize replay of a destructive operation and clearing local logs never changes server state. User-triggered audit export includes a preview of potential filename/tracker disclosure.

## Observability and streaming specifics

- **F08.07 port/NAT diagnostics:** Separately show phone listen port, backend-reported remote peer port, mapping status, test origin/result/time, network/VPN, and blocked/unknown states. A port test may be impossible from inside the same NAT and must not assert global reachability from local-only success. Explain the difference between rTorrent's public peer port and HTTPS remote administration port.
- **F08.10 graphs:** Offer optional speed/traffic and source-specific health charts from bounded timestamped samples, labeling gaps, polling interval, app-offline intervals, rate versus cumulative counters, byte-unit conventions and reset/rollover. Don't retroactively invent full histories or treat missed polls as measured zero.
- **F08.11 swarm health:** Distinguish current connected seeds/peers, tracker-reported totals, DHT-discovered candidates, torrent availability and actual verified byte growth. Last-seen time and backend source are mandatory for stale values; unavailable remote fields remain **unknown**.
- **F08.12 health checks:** Provide cancellable user-initiated **Check connection / Diagnose slow download** with stage-by-stage tested results (DNS/TLS/auth, transport, tracker, peers, actual received bytes, piece verification, storage capacity) only as permitted. Never invoke arbitrary external speed-test servers without user consent, and never use remote write commands to 'test' permissions. Record tested versus inferred causes and safe next actions.
- **F08.13 metadata export and change record:** Export a *reviewed, secret-scrubbed* torrent metainfo or a Chunks-only audit record independently. Private .torrent content may contain passkeys, so protected export requires explicit acknowledgement and no accidental public sharing. A status-change timeline is an observation history, not proof of who or what changed server-side state.
- **F09.02 seek-driven preview:** For locally downloaded partial content, an optional preview can request/boost required pieces using verified engine capabilities with bounded priority restoration and disclosure of performance impact. For remote file preview, byte-range streaming needs independent file-read authority from [EXTERNAL-FILE-ACCESS](EXTERNAL-FILE-ACCESS.md); plain XML-RPC torrent controls do not provide the file bytes. Missing headers/tails, unverified segments and files spanning unreceived pieces must produce explicit buffering/unavailable states rather than a false promise of playback.

## User journey and UI states

Every transfer has a shared expert **Connection / Peers / Pieces / Files / Diagnostics** area, with capability-aware tabs hidden or marked unavailable (never inert). The ordinary view remains minimal; high-risk operations live behind explicit expert controls. Diagnostics distinguish **last observed**, **configured**, **requested**, **verified** and **uncertain**. Every file or privacy mutation shows exact phone/server, root, affected torrent jobs, before/after and consequence for seeding. Network settings are opt-in and explain whether applied to the phone, one named remote, or selected environments. Use accessible textual labels as well as colors, explicit touched-unit legends, cancellation and reduced-motion alternatives.

## Recovery and verification

Treat remote disconnects, revoked Android URI grants, changed share roots, container remounts, file collisions and network/VPN transitions as invalidation of prior capability and byte/path proof. Read-only inspection is resumable; mutation retries require exact-target identity and fresh postcondition evidence. No untrusted local file, torrent metainfo, NFO, archive or peer message is executable. Extraction/password processing has bounded memory, CPU, nesting and output. All uploaded/transferred data remains opt-in and aligned with documented provider rules. A failed checksum does not authorize automatic file deletion.
