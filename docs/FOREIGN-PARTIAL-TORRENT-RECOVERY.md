# Recover pre-existing partial torrent payloads during local Add/Start

**Status:** Binding product behaviour. **P0 exact-path reuse: engine-level behaviour verified on the JVM libtorrent tier (12 November):** `LocalTorrentEngineTest.checkedAddReusesVerifiedExistingPartialPayloadAndRefetchesOnlyMissingPieces` and `restartedCheckedAddStillVerifiesExistingPartialPayloadInsteadOfTrustingInitialResume` prove that a pre-existing exact-path file holding the valid first half of the payload with one corrupted piece is hash-checked on Start, its valid pieces are kept, only the corrupted piece and the missing tail are downloaded, and the same holds after a process restart from the initial Add-time resume snapshot. The canonical Transfers row and the device controls now say `Checking existing data` while the phone engine reports its checking state (`UnifiedTransferObservation.checkingExistingData`, phone source only). Not yet done: separately surfaced verified-reusable versus still-missing byte counts, alternate-name (P1) and auxiliary (P2) recovery, and installed/physical acceptance. **Scope:** local Chunks engine and the user's selected, authorized **Chunks Downloads** Place (or explicitly changed local destination). Do not extend this to rTorrent server filesystem access. [TRANSFER-FILE-RECOVERY](TRANSFER-FILE-RECOVERY.md) governs repair of already-registered jobs whose paths subsequently change; this contract governs importing pre-existing bytes with a new or re-added local torrent.

**P1 detection/adoption primitives (13 November, JVM tier only, not wired to Add/UI):** `ForeignPartialLayoutScanner`, reversible no-replace `ForeignPartialRebind` and `ForeignPartialRecovery` are covered by unit tests plus `ForeignPartialRecoveryEngineTest` (real loopback libtorrent: a `.!qB` partial is adopted, hash-checked, and only missing pieces are fetched). Approval UI, Add integration, other fixtures and device proof remain open.

## Required behaviour

When a user Adds or Starts a local torrent, recognize plausible already-present payload data and **verify and reuse actual valid pieces before downloading missing pieces or claiming completed/seeding state**. This applies to stopped/re-added transfers, surviving data after app reinstallation/state loss, and files left by other torrent clients. Handle source-first Universal Add for `.torrent` immediately after metainfo validation and for magnets only once the **exact torrent metainfo and declared file layout** have arrived. Do not infer payload identity from title, filename, size, suffix or foreign resume metadata alone.

Ordinary exact-path data reuse must be automatic and decision-light. On Add with **Start when added** off, leave the job stopped after verification; with it on, preserve that intent and only begin ordinary downloading after path safety, necessary recovery approval and piece validation. A user pressing Start on a stopped existing job gets the same integrity protection. Do not auto-start from discovery or after unresolved approval/verification failures.

## Detection and client compatibility

1. Read verified torrent metadata (infohash, v1 piece hashes and/or v2 per-file Merkle verification, file-index/relative-path/size layout, pad files and v1 cross-file boundaries). Resolve the exact selected download root and torrent-relative paths, including top-level multifile directories.
2. Probe exact declared payload paths first without following symlinks. Accept existing regular files as candidates regardless of apparent completeness: clients can preallocate full logical sizes, create sparse files or leave short files. A pathname match provides no verified progress.
3. Only when exact paths are absent/incomplete or metadata permits a discriminating alternative, perform a **bounded read-only candidate scan** within the approved Place. Recognize common *configurable*, version-dependent conventions: qBittorrent `.!qB`; Transmission `.part` and its optional incomplete directory **only when that directory was chosen/authorized**; µTorrent/BitTorrent Classic `.!ut`; BitComet `.bc!`; configurable BiglyBT/Vuze and Tixati suffixes; normal files written by rTorrent/Deluge/libtorrent/aria2 and Android clients. Do not assume these defaults are exhaustive, and do not recursively scan all of Downloads, shared storage or other app-private directories.
4. Recognize but **do not delete or blindly ingest** auxiliary state: qBittorrent/libtorrent `.parts` (often used for skipped file boundary pieces), BitComet `*.piece_part.bc!`, Tixati fragment/partial-piece storage and aria2 `.aria2` control files. Foreign `.fastresume`, `resume.dat`, Deluge and rTorrent session metadata are only advisory until an exact, separately validated import adapter exists. They are never Chunks' native resume authority.
5. Record candidate provenance, observed relative path, accessibility, physical/logical size where available, format guess, and ambiguity. Distinguish *candidate detected*, *readable*, *hash verified*, *rebound*, *ready to resume*. No filename/suffix/size-derived percent complete.

## Verification and resume authority

- Prefer native libtorrent/libtorrent4j verification for v1, v2 and hybrid torrents; inspect the actual bound wrapper API for a supported `force_recheck` or equivalent and prove what it does on newly added *paused* jobs. Do not implement a competing Kotlin piece hash engine or assume wrappers expose all upstream APIs.
- **Require a real initial hash check whenever external existing bytes are adopted**, before network writes/seeding and before durable newly-created fast-resume bitfields can cause a future restore to skip checking. Chunks currently writes an initial resume snapshot during Add: coordinate native admission, checking and app-private resume commit so a zero-piece or stale bitfield cannot erase discoverable progress or falsely certify completion. On interrupted/check-failed verification, retain files and report unknown/needs recheck; restore must retry safely.
- Reuse only complete verified pieces. Sub-piece block data may be unavailable without authenticated matching resume/fragment format; do not claim it reusable. v1 pieces can straddle files, while v2's per-file hash tree and padding require accurate layout. Existing data with sparse holes, corrupt bytes or inappropriate offsets does not count.
- Persist a fresh Chunks-owned resume snapshot *after* confirmed verification and bind it to the correct torrent identity, effective storage Place, native handle generation and file layout. On later restart, treat modified or missing payloads as needing verification, not as valid merely because old fastresume metadata says so.
- Do not automatically download if the user selected Add stopped. While verification is active show Checking existing data, with measured/verified piece or byte counts only. Surface independently (a) bytes inspected, (b) bytes verified reusable, (c) selected bytes still missing, and (d) incomplete/unknown results.

## Alternative paths and unsafe collisions

If a foreign suffix, incomplete subfolder or differently named candidate is found, do not pretend libtorrent can directly access it at the declared path. Determine at runtime whether the exact libtorrent4j version supports a **non-mutating path mapping**. Upstream `rename_file` and `move_storage` can mutate files; neither may be described as a pure rebind. If a safe mapping is unavailable, offer a reviewed, minimal reversible rename/link/copy plan with exact source/destination, no automatic overwrite or deletion of foreign filenames/sidecars, explicit user approval for any filesystem modification, transactional journaling and readback. If a native expected pathname already contains different regular data, do not silently overwrite it as a side effect of a **foreign-layout repair**; distinguish this from the existing [local collision policy](LOCAL-TORRENT-COLLISION-POLICY.md), which authorizes ordinary engine writes at the torrent-declared target under the selected Place. Never allow two simultaneous jobs to write the same payload paths.

A sidecar whose format cannot be validated remains untouched. Recover normal verified pieces first; re-download any genuinely missing boundary pieces later under the user's Start choice. Never infer direct compatible partfile formats solely because two clients use libtorrent.

Refuse unsafe/unknown layouts, directory traversal, absolute metadata paths, symlinked components, special files, stale SAF grants and overlapping/aliased payload targets. Discovery is read-only and bounded; avoid blocking the UI, unbounded filesystem traversal or making a copy of the whole transfer by default. Stop/cancel and process death must leave an observable safe state; no blind replay of uncertain path-changing operations.

## User experience

Use existing Universal Add's source, target, **Save to**, **Start when added**, and single submission coordinator. No permanent Import wizard and no duplicate engine, catalog, state store or footer route. For a detected exact-path match, show a compact **Existing data detected; checking pieces** status with truthful verified reuse after checking. For ambiguous or foreign-layout candidates, offer a small optional **Review recovery** panel with candidate paths, safety implications, verification requirement and explicit approved action; allow Keep stopped/Skip candidate without losing the Add draft. Do not make the user choose from clients or upload their former client's resume database for ordinary cases.

## Staged implementation, dependencies and acceptance

**P0: Normal existing-file reuse.** Audit `LocalTorrentEngine.addStoppedChecked`, `addStopped`, `addMagnet`, `resume`, `restore`, `LocalPayloadCollisionSurvey`, `LocalResumeStore` and the app-private state writer. Implement exact-path verification with source- and handle-generation fencing, correct paused/Start choice, and no stale resume bitfield. Tests: empty, partial, complete, sparse/preallocated, corrupted, overlapping v1, v2, hybrid, stopped Add, started Add, re-add keeping data, app-state loss, process death during checking, mismatched fastresume, exact-path conflict, concurrent writers, and magnet metadata delayed. Actual real-peer continuation and seeding proof required.

**P1: Alternate file names.** Recognize `.!qB`, `.part`, `.!ut`, `.bc!`, configured variants and user-authorized incomplete folders; implement capability-proven rebind or approved reversible filesystem operation. Preserve foreign data and unrelated siblings; test duplicate plausible candidates, conflicting destination, readonly storage, canceled migration, stale filesystem observation, and no copy on ordinary exact-path cases.

**P2: Auxiliary partial-piece formats.** Independently research exact versioned `.parts`, `piece_part.bc!`, Tixati and aria2 control data; import only when format and torrent identity/offset mapping are verified in a specific adapter. Otherwise retain untouched, disclose limitations, and redownload missing pieces. Third-party resume metadata readers are optional accelerators and never establish verified completion on their own.

Qualify API 29/API 35 emulators, actual Pixel handset/Public Downloads/storage-grant behaviour and realistic interrupted source-client fixtures separately. Capture pre/post payload hashes, reused piece counts, missing-byte download delta, completed readback, seeding to an independent peer, restart restore, and failure/cleanup non-destruction. CI screenshot/text fixtures must trace these requirements rather than treating an exact obsolete screenshot as the product oracle.
