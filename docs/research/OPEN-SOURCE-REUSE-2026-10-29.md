**Researched 2026-10-29.** Non-normative implementation research, **not** another work queue. Source baseline: `main` `2202baa26ede143157a68de28dfb790ac3d49c01`; open shared-observation PR [#571](https://github.com/gamesbyian/Chunks/pull/571) must be reconciled live before model work. ## Existing Chunks public-Downloads proof found after initial research (correction, 2026-10-29)

The initial audit underestimated Chunks' implementation. [#387](https://github.com/gamesbyian/Chunks/pull/387) and [#436](https://github.com/gamesbyian/Chunks/pull/436) **already implemented and tested** a write-probed `Downloads/Chunks Downloads` native libtorrent save path, exact downloaded bytes, restart and seeding to a fresh peer on API35 and API29 emulators; see [LocalDownloadPlaces](https://github.com/gamesbyian/Chunks/blob/main/app/src/main/java/io/github/gamesbyian/chunks/LocalDownloadPlaces.kt), [native public Downloads test](https://github.com/gamesbyian/Chunks/blob/main/app/src/androidTest/java/io/github/gamesbyian/chunks/LocalPublicDownloadsPlaceInstrumentedTest.kt), and [QUALITY-LEDGER](../QUALITY-LEDGER.md#2026-10-28-android-10-downloads-restart-persistence-and-seedhost-add-ui-journey). **Do not build an alternative disk I/O backend just to provide this existing baseline.** LibreTorrent SAF and custom libtorrent disk I/O are contingency/research paths for *unmet* provider/permission requirements, not default P0 implementation. #568's remaining gates: physical handset, reinstall ownership, permission changes, removable and non-POSIX providers, crash durability. The baseline has no `MANAGE_EXTERNAL_STORAGE` requirement on supported versions. This correction preserves the remaining reuse references below.

## Decision in 90 seconds

1. **Preserve Chunks' already proven public-Downloads native engine path, then consult LibreTorrent SAF/service source only for unmet provider and lifecycle scenarios (#568/#569)**. It uses the same libtorrent4j family, has a real `SafFileSystem`/file-descriptor abstraction and documents a POSIX disk-I/O option. Yet its **broad storage permission and version-specific behavior must not be mistaken for a Play-compliant universal Downloads solution**. Existing Chunks emulator fixtures prove native piece writes and resume for public Downloads. Target physical-device, permission and non-POSIX provider cases next; do not transplant GPL implementation by default.
2. **Read upstream libtorrent's current `disk_interface` and qBittorrent's `CustomDiskIOThread`** before designing a storage bridge. The 2.x extension point is **session-level**, not the old per-torrent `storage_interface`. Verify what libtorrent4j actually exposes through SWIG and whether a native fork would be required.
3. **Use Flood's rTorrent adapter, method-call configuration and disposable-client test rig as the primary remote-core reference (#1/#4/#9)**. It uses a single-concurrency request queue, explicit XML/JSON capability and actual rTorrent integration testing; adapt semantics, not its Node server/JWT or GPL source wholesale.
4. **Use Transdroid's `IDaemonAdapter` and rTorrent adapter as an independent second implementation** to expose method, authentication, path and XML-RPC compatibility cases. Use ruTorrent's HTTPRPC, Ratio and Throttle plugins as **protocol and behavior specifications** when those plugins are present, not assumed remote features.
5. **For shared environments (#567), normalize observed data before UI migration**. Flood's request-manager → gateway → normalization pattern and BiglyBT Android's local/remote session separation are directly useful. An optional cross-engine projection must not become command authority; missing/stale values and exact profile IDs remain explicit.

**Copying policy:** this repo has not made a new licensing choice here. MIT/BSD/Apache-2.0 candidates are eligible for a reviewed *code import* with provenance, NOTICE/attribution and dependency audit. GPLv3/GPLv2+ apps are candidates for behavior, architecture, tests and independent reimplementation unless their copyleft obligations and the intended Chunks distribution license are deliberately accepted. Publication as open-source by itself does **not** grant unrestricted code mixing. A GitHub release from another project does not prove an approach works on the current Chunks target SDK.

### Critical P0 Android questions before implementing a storage adapter

- **Permissions:** On Android 11+, the SAF tree picker cannot grant the Download root ([Android document restrictions](https://developer.android.com/training/data-storage/shared/documents-files)); opening an individual file or a user-selectable permitted **subfolder** and creating `MediaStore.Downloads` entries are different operations. Do not infer that `Downloads/Chunks Downloads` is equivalent to a user-granted unrestricted POSIX directory.
- **Native random I/O:** prove that target provider permits `pread/pwrite/lseek/fsync`, effective close/durability, multi-file/truncated writes, missing permissions, restart and hash checking; distinguish detached export from backing bytes. [Android DocumentFile limitations](https://developer.android.com/reference/androidx/documentfile/provider/DocumentFile) and [rclone SAF provider](https://github.com/makifves/rclone-for-android) illustrate opaque URIs and provider-dependent consistency, including async-close caveats.
- **Execution:** Android 15+ `dataSync` foreground services have **six hours total per 24-hour background interval**, with `onTimeout` mandatory; [official documentation](https://developer.android.com/develop/background-work/services/fgs/timeout). Assess [user-initiated data transfer jobs](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options) and WorkManager within actual permission/behavior limits; neither is proven capable of indefinite unattended seeding. No declaration trick or unsupported special-use type.
- **Decision gate:** first benchmark current libtorrent4j + POSIX I/O on app-private and allowed real destinations. If insufficient, test a tiny native `disk_interface` prototype with scoped FD strategy; only then consider a customized libtorrent4j binary. **No automatic path migration** before a rollback plan and existing resume data remain intact.

## F. Findings not to overclaim

- **"Full-featured Android torrent app" does not prove indefinite seeding** on Chunks' newest target SDK, release policy, hardware, network or service lifetime.
- **"Supports SAF/SD" does not prove native torrent piece writes on arbitrary Android providers**, nor access to the protected Download root. It may mean broad all-files permission or copy-on-complete. Audit actual code and lifecycle.
- **"rTorrent can move a torrent" does not prove disk bytes move safely**, especially across volumes or in the absence of a server-owned journal. Flood explicitly needs the same filesystem view to touch files.
- **The ability to call an RPC method does not prove authorization**, tenant preservation, idempotence or a verified postcondition. Never implement "retry until success" after an uncertain mutating acknowledgement.
- **A permissively licensed application can have nonpermissive dependencies/assets**. Record commit, relevant file header, package/license scope, notices, cross-licence issues and tests before importing source. A language, framework or UI mismatch may make architecture reuse cheaper than a port.
- **Upstream documentation is not pinned acceptance.** GitHub default branches and README claims may have changed; the code-level spot checks listed here are not a full audit of every relevant subsystem. A prototype and independently measured bytes are still mandatory.
