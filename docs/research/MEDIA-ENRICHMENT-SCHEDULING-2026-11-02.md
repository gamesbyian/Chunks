# Offline-first metadata dispatch planning (2026-11-02)

**Status:** pure Kotlin scheduling-policy model merged via [#1070](https://github.com/gamesbyian/Chunks/pull/1070), with a follow-up scheduling-correctness regression. No active provider HTTP calls, no Android service, no scheduled/background work, no release obligation. Uses the versioned typed cache key and `FETCH_ELIGIBLE` outcome merged via [#1053](https://github.com/gamesbyian/Chunks/pull/1053).

`MediaEnrichmentDispatchPlanner` maps already-authorized queued typed entity IDs, per-provider budgets, cache decisions and explicit device conditions to a *deterministic suggestion to send*, **not to a network operation**. The caller constructs intents only from user-requested enrichment or previously consented asynchronous inventory work. Opening Similar Transfers or a transfer-details pane never produces intents. The host must atomically reserve each selected request before issuing real HTTP, persist authoritative quota and negative-cache receipts, cancel on consent revocation/lock, retry only after confirmed provider conditions and never expose remote paths or tracker credentials.

Key gates: provider individually approved, global enrichment consent, source member currently authorized and visible, cache state exactly `FETCH_ELIGIBLE`, network online, bounded batch, provider-specific minimum interval, cooldown, remaining requests and in-flight concurrency. On metered networks or power saver, background lookups defer; explicitly user-requested lookups may proceed subject to all other gates. Shared provider entity IDs are deduplicated across environments. User-initiated work outranks background, with oldest-first ordering within priority; future-dated intents and clocks older than previous dispatch time fail closed. At most one request per provider is returned per selection batch, preventing a burst from a same-tick planner invocation. This is intentionally conservative even for providers permitting higher concurrency.

**Source terms to configure later, not defaults hardcoded into model:**
- [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API) requires meaningful User-Agent, noncommercial free service and at most one request/second per client; [rate limits](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting) may refuse with HTTP 503. Core CC0 and supplementary CC BY-NC-SA rights are separate: [licenses](https://musicbrainz.org/doc/About/Data_License).
- [Open Library](https://openlibrary.org/developers/api) uses one request/second default, three when properly identified, user-directed/cached reads and published dumps for bulk requirements. It is not a general backend crawler.
- [Metron](https://github.com/Metron-Project/metron/blob/master/api/README.md) requires authenticated reads, has conditional detail request support; terms/auth/cache/attribution still need approval.
- [TMDB](https://developer.themoviedb.org/docs/faq) noncommercial API and attribution terms remain separately gated.

**Tests:** nine local host Kotlin/JUnit-compatible behavior tests passed against the exact versioned cache-model sources from #1053, covering offline/consent/provider failure, visibility changes, metered/power gating, typed deduplication, one-per-provider ordering, cooldown/quota/concurrency, cache ineligibility, oldest-first fairness, clock rollback and duplicate budgets. These are *not* Gradle or Android results, actual provider throttling, secure persistence or release acceptance.

**Not implemented:** background WorkManager/AlarmManager, credential handling, HTTP clients, legal provider agreements, normalized SQLite persistence, cellular policy UI, cross-process quota leases, provider 304/404/429/503 parsing, battery tests, or actual opt-in consent UX. Integration must happen only after #1053/#1031 and P0.

## Due-time eligibility before priority deduplication (2026-11-02 follow-up)

A future-dated user intent must **never** promote a currently due, consented background intent for the same typed provider key. In the original grouping order, `min(queuedAt)` across background and future user intents combined with `USER_REQUEST` from *any* authorized reference could cause a background request to be classified as user-directed and bypass the metered-network or power-saver restriction. Correct by filtering due and currently visible/authorized intents **before** deduplicating by key and selecting user priority. At the due time, the user request legitimately wins; on an unmetered connection before that time, the background request retains background status.

**Local verification:** nine existing pure-Kotlin planner tests plus three explicit time/visibility/consent-priority regressions, **12/12 passed** with host `kotlinc` and minimal JUnit-compatible stubs; the test sources and model were hashed before GitHub submission. No real HTTP dispatch, process-persistent reservations, Android behavior or provider quota correctness is claimed. Exact-head CI remains mandatory before merge.
