## Relationship fact semantics

A typed entity is `(source namespace, kind, exact ID)`. Episode, film, book work, edition, comics issue, person, character, fictional universe, production, recording and game are distinct types. No title-match identity, numeric-ID namespace collapse or automatic same-work merge. Directional facts include `ADAPTED_FROM`, `REMAKE_OF`, `SEQUEL_TO` and `EDITION_OF`; queries display reverse direction explicitly. Typed shared-node relations cover exact same writer, creator, performer, actor, a film's biographical subject and album performer, common high-specificity topic, character, shared universe, series, and production entity. No unbounded graph walks: at most two eligible fact edges and no cross-role joins except **about-person ↔ performer**. High-degree intermediate terms (more than 256 incoming statements) are omitted from default candidate discovery rather than causing unbounded work or overly broad recommendations. This threshold is a provisional implementation safeguard, not a measured Android performance budget.

Each provider field assertion is addressable by `(provider, sanitized record key, field key)` with monotonic revision and `VERIFIED`, `USER_CONFIRMED`, `INFERRED`, `DISPUTED` or `RETRACTED` state. Only confirmed evidence from an explicitly approved provider is eligible for suggestions. Source-field revision conflicts, explicit disputes to the same edge and unsupported topic specificity **fail closed**. Explainable matches retain original source claims and intermediate typed ID. The source inventory must supply an explicit set of privacy-authorized **visible entity IDs**; even a verified relation is not visible otherwise. Source withdrawal/revocation rebuilds an independent derived graph without changing torrent state.

**Important limitations:** The component does not resolve Wikidata QIDs or validate provider credentials/schemas by itself. The adapters must pass canonical IDs only after exact crosswalk validation and preserve source timestamps, rights and credit/episode/issue granularity. `USER_CONFIRMED` means an explicit, scoped correction recorded by the existing identity correction path, not a silent name heuristic. No UI may interpret `MediaGraphRelation` ranking as statistical probability or infer issue-range coverage from one member. The component does not itself map entity IDs to exact environment/profile/infohash transfer keys; #1031 and the canonical scoped inventory retain that responsibility. Separate physical-device and collection-coverage tests are still required.

## Offline enrichment receipt and retry semantics

`MediaEnrichmentCachePolicy` is a **decision-only** component. Its cache key is a typed provider entity ID, never a filename, torrent hash, password or private path. Its versioned receipts distinguish verified positive, 404 negative cache, rate limit, transient failure and unsupported schema. Providers supply **their own legal TTL and backoff**, not arbitrary universal durations. Consent, source approval and visibility gate all decisions, including fresh cached data. A valid positive receipt can contribute to locally confirmed relationships only **before** its configured expiry and for the matching normalization schema version. Expired positives can support explicitly allowed, clearly labelled stale **display only**, never fresh inference; an offline miss never triggers access. 404 caches suppress pointless immediate retries, 429/503 cooldowns are honored, conflicting same-revision receipts quarantine, and an unknown schema requires explicit requalification. `FETCH_ELIGIBLE` is not permission to perform a network request on opening transfer details; the separate consent-aware, rate-limited enrichment queue must schedule it.

**Important limitation:** Receipts contain no provider JSON or artwork. Actual encrypted persistence, SQLite migrations, conditional HTTP requests, provider-specific retry-after interpretation, consent removal wiping licensed payloads, structured license/attribution storage and record-level validity remain future integration work. This model must never be used to declare provider licenses approved or cache third-party payload against source terms.

## Research re-check (2026-11-02)

- **TVmaze** documents an episode guest crew endpoint (`/episodes/:id/guestcrew`), HTTP cache window of 60 minutes, at least 20 calls per 10 seconds per IP, `429` backoff and CC BY-SA API licensing: https://www.tvmaze.com/api . Whether episode #43454 returns a machine-readable writer/ID pairing remains **unverified in a captured JSON fixture**.
- **MusicBrainz** requires a meaningful User-Agent; free web service is for noncommercial use and limits each client to **one call/second**, with IP-based overload failures: https://musicbrainz.org/doc/MusicBrainz_API and https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting . Artist/recording/release-group/release IDs must never be conflated.
- **Open Library** emphasizes user-directed, low-volume reads and caching, default **one request/second** and **three requests/second** when properly identified, and advises **published dumps** rather than bulk API scraping: https://openlibrary.org/developers/api . ISBN refers to editions, not necessarily a unique abstract work.
- **TMDB** requires registration, attribution, specific branding and a separately negotiated commercial license; free API only for noncommercial use: https://developer.themoviedb.org/docs/faq . Do not bake registered credentials into APK.
- **Wikidata** exposes a versioned Wikibase REST API for typed claims and source-specific rate limits: https://www.wikidata.org/wiki/Wikidata:REST_API . Use bounded individual-entity claims and references; do not presume any QID bridge is complete or universally correct.

These are **documentation checks**, not live API acceptance. Next independent gates: small lawful actual response JSON recordings with source version/license, provider-ID/role contract tests, multi-member issue coverage and correction/retraction fixtures, and warm indexed Android performance. Do not allow media work to block P0 Add/Start/durability/transport delivery.
