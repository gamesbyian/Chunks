## Screen ownership and hierarchy

- Beneath the compact **chunks.** wordmark show the **Connections** heading and **one list of remote profiles**. Each saved remote appears **exactly once**, even when its session is active. Never render separate cards for the same profile under Connected and Saved servers; do not duplicate its action set. Profile identity is the stable saved profile ID, **not** its display name or server hostname. Distinct numbered endpoints on one host remain distinct.
- Sort profiles with **currently verified connected** profiles first. Other saved profiles follow in stable existing/user order (or predictable alphabetical order if no existing stable user order). Avoid reordering during transient refresh/polling, scrolling or pending operations; keep focus and card identity stable. A profile needing attention remains in the list with a truthful status and action.
- Each compact card shows the **user's short connection name**, a clear **Connected / Disconnected / Needs attention** state and, only when reliable and useful, compact context such as last verified connection or current default downloads destination. Status is **not** inferred from whether credentials are saved or a cached inventory exists. Display stale/unverified state appropriately, without falsely asserting a live connection or zero jobs.
- Primary actions: for **Connected**, **View transfers** and **Manage**; for **Disconnected**, **Connect** and **Manage**; for **Needs attention**, **Reconnect / Resolve issue** as appropriate and **Manage**. **View transfers** always opens the *canonical* Transfers screen filtered to that exact profile identity, preserving its authentication/privacy policy and truthful cached/refreshing/unknown inventory state. A disconnected saved profile may still have access to an explicitly supported read-only inventory path; do not imply a verified interactive session merely because read-only browsing succeeds.
- **Manage** opens one dedicated exact-profile settings surface. Move the long endpoint URL, edit/rename, environment colour, default remote folder, saved login/remember-login preference, server tools (when supported), Disconnect, Forget profile and diagnostic explanations here. Use existing verified, transactional and destructive-action confirmation boundaries. No unreviewed state-changing RPC merely from opening Manage, reading inventory or selecting a card. A saved profile without a current verified session is still manageable as a saved configuration.
- With **one or more profiles**, keep a compact, consistently visible **+ Add connection** action adjacent to or after the roster; it must remain discoverable without excessive scrolling and be available for 1/N profiles, including failures/locked profiles. Do not retain the large introductory card on this populated view.
- With **zero saved profiles**, show one compact purple onboarding card titled **Connect to a remote client** and a single plain-language description, for example **Manage torrents on another computer or server.** Put **+ Add connection inside that card**, not beneath it. Remove “(optional)” from the heading and the lengthy seedbox/rTorrent/endpoint/protocol and safe-review explanation from the landing view. Keep necessary privacy/auth/security explanations contextually in Add/Edit/Manage rather than dropping the actual safeguards.
- Maintain the fixed **Transfers / + Add / Connections / Options** footer throughout. Connection creation success returns to the unified Connections roster with a concise acknowledgement, and never inserts a parallel active-connection panel.

## Profile and session semantics (do not conflate)

A **saved profile** is persisted endpoint/alias/configuration and possibly remembered credentials; a **connected session** is an independently confirmed current capability/authentication state. A saved profile may be disconnected, expired, inaccessible, locked, or in error without disappearing or losing its settings. A currently usable unsaved session, if supported, should appear **once** as a transient profile card with a clearly labelled unsaved state; do not silently imply it has been remembered. The remember-login setting is distinct from remembering the nonsecret connection profile.

Use unambiguous read-only vs mutation authority for exact profile identity. A successful inventory read from stored credentials is not in itself proof that a user explicitly connected for mutation or granted durable privacy access. Preserve existing per-profile locks, server routing, separate credential boundaries, unknown/stale counts and exact-authority rules. Disconnect does not mean Forget, and Forget must respect any existing confirmation/data-retention contracts. Do not silently switch to a different server when a session fails.
