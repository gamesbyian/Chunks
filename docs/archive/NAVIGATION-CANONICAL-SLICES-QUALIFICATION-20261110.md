### Explicit Disconnect versus saved-login startup restoration

A saved verified login could previously cause an immediate automated reconnect when a user explicitly tapped **Disconnect** while the initial startup reconnect token had not yet been consumed. The same Disconnect handler is used by Connections and the older authenticated operational view.

The navigation stack now marks startup reconnect attempted and also records a **separate** `rememberSaveable` deliberate-disconnect suppression bit **before** clearing the authenticated session. The cold-read-only reconnect effect (including restored Combined entry) checks both bits. Saving the transient startup-attempt bit itself would incorrectly suppress normal process-death restoration, so that token remains unsaved. Only a newly **verified** authenticated Connect clears deliberate suppression; a failed manual attempt does not restore automatic-retry authority.

Installed disposable two-server coverage now requires: verified A → explicit Disconnect → stable manual connection form → Android Activity recreation → still no implicit reconnect → explicitly Connect B → continue exact-account union, same-hash Details, Start/Stop, C2 timeout/auth/offline and separate process-death read-only resume. This is a test contract and implementation, not a claim that the newest exact-head run has already passed.

Saved Connections actions now provide exact endpoint-specific TalkBack names for View, Use saved login, Rename and Forget, including duplicate friendly names. Compose tests assert exact immutable account selection and two-across controls with 48dp minimum targets at 320dp/200% text. New heads are still awaiting CI.
