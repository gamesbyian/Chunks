# Find existing files and restore a broken transfer

**Status:** normative planned feature. No implementation, live server execution, or integrity verification is claimed. Governing documents: [PRODUCT](PRODUCT.md), [UX](UX.md), [ARCHITECTURE](ARCHITECTURE.md), [SECURITY](SECURITY.md), [STORAGE-AND-EXTRACTION](STORAGE-AND-EXTRACTION.md), [UNIFIED-ENVIRONMENTS](UNIFIED-ENVIRONMENTS.md), and [RTORRENT-COMPATIBILITY-MATRIX](RTORRENT-COMPATIBILITY-MATRIX.md).

## User goal

When files backing an existing torrent have been renamed or moved **outside Chunks** (FTP/SFTP, ruTorrent, shell, file manager or another client), offer **Find files to restore transfer** from broken/inaccessible transfers, transfer details, file tree and optional multi-select repair wizard. Reconnect original torrent job to surviving data *in place*, without reverting user filenames, forcing full download, creating needless duplicates, deleting content or changing the torrent's infohash. This is a companion to rename-without-breaking: the earlier action is proactive; this one repairs external drift. Unrelated server outages, permission failures, unchecked pieces and missing bytes must not be mislabeled as path breakage.

## Diagnose before assuming

Read the exact environment/profile, torrent infohash, original metainfo file entries, file indices, lengths, offsets/piece hashes and current engine effective paths/mapping, download directory, file selection and expected completion. Use read-only freshness/capability probes. Signals include missing backing paths, engine I/O errors, vanished files and external renames/moves; error alone does not prove displacement. Separate **offline**, **authentication/permission**, **storage error**, **path mismatch**, **unverified content**, **missing bytes**, and **unknown**. Do not scan arbitrary remote filesystems or private sibling profiles without explicit user-selected authorized roots.

## Recovery wizard

1. **Find:** Present old expected path and file counts with exact phone/server identity. User picks a new directory/root or authorizes a bounded search within selected Places. Search for plausible relocated/renamed files from safe filename similarity, retained technical tags, size (including partial sizes), known directory movement, companion files and safe indexed metadata. Never rely on basename alone. On remote seedboxes require a *separate, proven* file listing/stat/read capability (SFTP, authorized provider FS, etc.), not just rTorrent XML-RPC.
2. **Match:** Explain per-file candidate, observed path, size, evidence and ambiguity. Distinguish plausible/likely from **verified**. Validate content by hashing against torrent piece hashes or v2 per-file hashes as applicable, respecting v1 pieces that span file boundaries, pad files, holes, sparse/incomplete data and differing piece completion. Optional bounded probes reduce candidates; they do **not** certify a file. A size match, name similarity, or byte sample never establishes full torrent integrity. If no authorized read or hash access exists, offer manual guidance/metadata-only candidate selection but **do not claim restored data**.
3. **Plan:** Build stable file-index → effective backing-path map; offer whole-root rebasing for folders moved together and per-file mapping for differently renamed/moved items. Show changed **engine mapping** separately from physical filesystem operations. Prefer a non-mutating path rebind. Alternative explicit safe hardlink/reflink or file copy into expected layout only if authorized and supported; hardlinks share writable data. Never force original naming, overwrite, relocate or delete user files by default.
4. **Apply:** Gate on exact engine version/API compatibility and filesystem backing. Stop/quiesce the affected torrent as needed; checkpoint relevant state (mapping, directory, selections/priorities, fast-resume, stop/started state) and perform capability-proven rebind or carefully reviewed alternative. Revalidate identity and paths immediately before execution. rTorrent `d.directory.set`/related variants primarily address compatible root changes and have version-/single-vs-multifile semantics; don't assume support for arbitrary file-index mapping. rTorrent RPC success does not prove bytes or path mapping. No blind use of generic RPC as a filesystem API.
5. **Verify:** Perform engine readback and actual hash/piece recheck, observing finish/error; recheck may pause network participation and take time. Resume only after the mapped, verified surviving pieces are recognized and user policy permits; incomplete torrents continue downloading genuinely missing pieces. Preserve download/seed history and priorities where feasible; show exact number of verified pieces, selected missing bytes and remaining failures. An interrupted or uncertain action requires journaled read-only reconciliation before any retry.

## Engine distinctions

- **Local Arvid libtorrent4j:** upstream libtorrent supports `torrent_handle::rename_file`, `move_storage`, `get_renamed_files` and `force_recheck`. Those operations have different side effects; `rename_file` itself can rename an on-disk file, and `move_storage` may copy/move/replace content. The UI MUST NOT invoke these as a pretend non-mutating rebind. Determine precise libtorrent4j bindings and whether a true map-to-existing-path operation is available; otherwise require an independently approved safe linking/copy plan. Never use `always_replace_files` as recovery default.
- **Remote rTorrent:** versioned `d.directory.set`/`d.directory_base.set`, stop/close/start and hash-check sequences may restore an entire moved directory when its internal names still match. Different file names and arbitrarily scattered file paths need verified per-file mapping support or a filesystem capability that safely presents the required original names (such as user-approved hardlinks in a compatible filesystem). Standard XML-RPC cannot be assumed to relink any arbitrary file. Capability-test the actual seedbox instance and protect exact numbered instance/tenant boundaries.
- **FTP-only:** naming/listing may be possible but no engine rebind or hashing authority; an FTP directory rearrangement is *not itself* sufficient to guarantee restoration. Never claim success based on successful FTP file operations.

## UX and safety rules

- Default read-only **Scan/Preview**. Highlight *found files*, *strong candidates*, *content-verified*, *relinked*, and *resumed* as distinct stages. Explicit confirmation before engine changes, hardlinks/copies or any potentially mutating filesystem operation; display estimated I/O/time where measurable and never invent progress.
- A one-tap suggested root fix is allowed only after the matching path relation is proven and subsequent verification is still required. Batch repair groups compatible candidate moves, isolates errors per transfer and prevents cross-torrent/path contamination. Shared files and duplicate candidates require explicit accounting. Preserve aliases, Plex-oriented user names, external filename modifications and metadata separately from torrent's immutable infohash and original entries.
- No files deleted, overwritten, renamed back, or re-downloaded as a *repair side effect*. Normal subsequent downloading of genuinely absent pieces requires user-visible intent. Avoid filesystem-wide hashing without bounded scan budgets, cancellation, symlink containment, root allowlists, privacy lock and resource controls.
- Security: local SAF/provider grants and remote ACL, TLS/SSH host validation, exact authorized Place scopes, secret isolation, path traversal/symlink escape protection, adversarial filename sanitization, journal persistence and reconciliation. Do not use a broad elevated helper for ordinary rTorrent control.

## Acceptance

Fixtures: unchanged folder relocated under another parent; single-file torrent renamed; multifile torrent with one episode renamed and others moved; directories split; Plex-style minimal rename with codec/release group preserved; partial pieces; duplicate names and sizes with different hashes; v1 cross-file pieces; v2 pieces; encrypted/no-read remote; server unavailable; unexpected user writes during scan; shared hardlinks; failed RPC after write; interrupted restore; same-hash jobs in two server profiles. Unit tests assert zero automatic source mutations and abstention on ambiguity. Local engine tests prove resume/seed after hash recheck. Remote testing requires approved nonsecret instance, exact version/RPC/FS access evidence, seedable public fixtures, and genuine post-repair peer/hash behavior. All physical acceptance and current coverage belong in [SPEC-COVERAGE](SPEC-COVERAGE.md) and [QUALITY-LEDGER](QUALITY-LEDGER.md).
